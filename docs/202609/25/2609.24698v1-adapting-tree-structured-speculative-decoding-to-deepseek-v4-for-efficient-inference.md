## 摘要
自回归解码过程中对目标模型的重复执行是大语言模型推理延迟的主要来源。与沿单条候选链展开的线性推测不同，树结构推测从共享前缀出发保留多条分支；在相同预算下，这种更广的覆盖范围可提升接受率与效率。将其适配到 DeepSeek-V4 并非易事：其 CSA/HCA 在线压缩注意力将难点集中在目标验证一侧，从共享前缀分出的各分支会被压缩为不同的状态，从而破坏跨分支的状态一致性。我们通过分支感知的因果验证、临时状态隔离以及接受路径状态刷新，将树结构推测解码集成到 DeepSeek-V4-Flash 流水线中，使验证与压缩状态更新在各分支间保持一致。在预算 D=5 至 D=8、批大小 1 至 64 以及三个数据集（GSM8K、MBPP、ShareGPT）上，树结构推测在所有设置中取得的接受长度均高于与之匹配的线性配置（例如 D=8 时约为 2.83–3.41，而线性为 2.39–2.84），并在几乎所有配置下提升了吞吐量——仅在最小预算下提升有限——最高约 18.5%。更重要的是，这些增益遵循稳定且可迁移的规律：相对增益随预算增大而提高，并在中小批大小下对可预测性较低的工作负载最为显著；而超过某一预算后，吞吐量趋于平台期，并与仍在上升的接受长度解耦。这些结果表明，在相同预算下保留多条候选路径能够有效提升 DeepSeek-V4 的解码效率，并为将推测解码适配到未来具有压缩、稀疏或结构化上下文表示的模型提供了经验。

## Abstract
Repeated execution of the target model during autoregressive decoding is a major source of LLM inference latency. Unlike linear speculation, which follows a single candidate chain, tree-structured speculation retains multiple branches from shared prefixes; under the same budget, this broader coverage can improve acceptance and efficiency. Adapting it to DeepSeek-V4 is nontrivial: its CSA/HCA online compressed attention concentrates the difficulty on the target-verify side, where branches diverging from a shared prefix compress into different states, breaking cross-branch state consistency. We integrate tree-structured speculative decoding into the DeepSeek-V4-Flash pipeline via branch-aware causal verification, temporary state isolation, and accepted-path state refresh, keeping verification and compressed-state updates consistent across branches. Across budgets D=5 to D=8, batch sizes 1 to 64, and three datasets (GSM8K, MBPP, ShareGPT), tree speculation achieves a higher accepted length than the matched linear configurations in all settings (e.g., at D=8 about 2.83--3.41 versus 2.39--2.84) and improves throughput in nearly all configurations---marginal only at the smallest budget---by up to about 18.5%. More importantly, the gains follow stable, transferable regularities: the relative gain grows with the budget and is most pronounced for less predictable workloads at small-to-medium batch sizes, while beyond a certain budget throughput plateaus and decouples from the still-rising accepted length. These results show that retaining multiple candidate paths under the same budget can effectively improve DeepSeek-V4 decoding efficiency, and offer experience for adapting speculative decoding to future models with compressed, sparse, or structured context representations.

# 论文总结：将树结构推测解码适配到 DeepSeek-V4 以实现高效推理

## 1. 核心问题与整体含义（研究动机与背景）

- **背景痛点**：大语言模型（LLM）自回归解码需为每个新 token 重复执行目标模型前向，是推理延迟的主要来源；长上下文模型（如 DeepSeek-V4）因注意力计算与上下文管理开销，问题更突出。
- **推测解码的既有思路**：EAGLE-3/MTP 风格中，轻量草稿模型预测多个未来 token，目标模型一次前向批量验证，从而摊薄目标模型调用成本；每轮接受 token 数决定了解码吞吐。
- **线性 vs 树结构的根本差异**：
  - 线性推测沿单条候选链展开，链首预测错误会导致整段后缀失效。
  - 树结构推测从共享前缀保留多条分支，在**相同验证预算**下覆盖更广，理论上可提升接受率。
- **适配 DeepSeek-V4 的独特难点**：DeepSeek-V4 采用 CSA（Compressed Sparse Attention）+ HCA（Heavily Compressed Attention）在线压缩注意力，上下文被序列级压缩。当候选形成多分支时，逻辑祖先关系与物理顺序不再一致，从共享前缀分出的各分支会被压缩为**不同状态**，破坏跨分支状态一致性。
- **核心论断**：难点不在构造候选树，而在**目标验证侧**——必须在主动压缩、重组上下文的注意力系统中，保持树推测语义、因果可见性与压缩状态的一致性。

## 2. 方法论

### 2.1 核心思想
将推测推理组织为三阶段前向流程，并明确区分**持久参考状态（已接受前缀）**与**临时分支状态（未验证候选）**，只有被选中的接受路径才能提交到持久上下文。

### 2.2 三阶段推测前向
1. **Draft extend（草稿扩展）**：将已接受前缀扩展为候选分支并组织成树，树形取决于草稿输出、分支参数与验证预算。
2. **Draft decode（草稿解码）**：在树拓扑下计算草稿侧表示，每个候选仅关注其祖先路径；DeepSeek-V4 的 FlashMLA/注意力路径已支持树注意力，适配主要提供候选布局与注意力元数据。
3. **Target verify（目标验证）**：验证前通过 verify preprocess 把候选树转为验证计划，定义候选链抽取方式与**压缩边界**（共享前缀可复用状态，分叉后各链必须独立压缩，避免混入互斥历史）；验证后选出接受路径并仅提交该路径状态。

### 2.3 临时分支状态与压缩状态处理
- **SWA 与 CSA/HCA 的区别**：SWA 仅需 token 级 KV 刷新（保留接受路径、丢弃拒绝分支）；CSA/HCA 需为每条候选链维护**隔离的压缩状态**（压缩 token、压缩注意力状态、压缩中间缓冲）。
- **Scratch pad（暂存区）**：存放临时分支状态直至验证完成，避免推测分支在有效性未知前写入持久缓存；同时规避 DeepSeek-V4 页式 KV 缓存池（一逻辑层 + 三物理层、共享页指针）在分支探索期的页分配/所有权/回收复杂度。
- **接受路径状态刷新**：选定路径后刷新其 token 历史、KV 状态、CSA/HCA 压缩状态及压缩中间缓冲，拒绝分支状态不进入下一轮。

### 2.4 性能优化
- **Scratch-pad 执行**：减少持久缓存流量；若仅单候选链或接受链已是最近缓存链，可跳过刷新。
- **C4/C128 差异化刷新调度**：C4 压缩频繁，需及时更新压缩状态与中间缓冲；C128 压缩稀疏，部分写入可延迟并合并到接受路径确定后。
- **设备端元数据处理**：候选索引、链边界、验证计划元数据在设备端准备/变换，减少主机控制开销，实现主机调度、GPU 元数据处理与目标模型执行的流水重叠。
- **CUDA Graph 覆盖有界化**：由候选链数与草稿/验证参数估算图上限，覆盖常见树形而不造成闲置图容量带来的显存浪费。
- **元数据复用**：草稿侧候选布局与元数据尽可能复用于目标验证。

### 2.5 系统集成
整体流程集成到 **SGLang**：接受前缀与持久缓存 → draft extend → draft decode → verify preprocess → 分支感知目标验证（临时状态入 scratch pad）→ 接受路径选择 → 状态刷新（含 C4/C128 特定更新）→ 返回 SGLang 进入下一轮迭代。

## 6. 主要结论与发现

1. **接受长度全面提升**：所有预算与批大小下，树配置接受长度均高于匹配线性配置；D=8 时约 2.83–3.41 vs 线性 2.39–2.84。
2. **相对增益随预算单调增长**：D=5 约 +11.0% → D=6 +14.4% → D=7 +17.1% → D=8 +18.6%；线性基线几乎不随预算变化（≈2.84/2.67/2.39），增益完全来自树侧，且每档增量递减（+3.4%/+2.6%/+1.6%），反映链长趋近草稿可靠预测边界。
3. **接受长度几乎不随批大小变化**（<0.04），从而把吞吐的批大小依赖干净地归因于执行层面。
4. **加深链无额外收益**：同预算下"浅而宽"与"深而窄"差异约 2% 以内；草稿能力瓶颈在质量而非预算，拓宽是提升接受上限的另一路径。
5. **吞吐提升**：多数配置正向，D=5 少数接近打平；平均增益约 +3–5%（D=5）→ +8–9%（D=6）→ 平台约 +9–10%（D=7/8）；**峰值 +18.5%**（s3_k2_d6, bs=4, ShareGPT）。
6. **吞吐与接受长度在 D≈6 后解耦**：更多预算买到质量但买不到速度（额外接受收益缩小、开销增大相抵）。
7. **批大小呈倒 U 形**：峰值约在 bs=4（D=6 时 bs1 +8% → bs4 +11% → bs64 +7%）；小 batch 记忆受限、接受更多 token 直接减少目标前向；大 batch 计算受限，额外候选争抢算力。
8. **最难预测的工作负载收益最大**：ShareGPT 最高，GSM8K/MBPP 略低，与接受长度趋势一致。
9. **与草稿侧方案正交**：DSpark 等改进草稿侧，本文改进验证侧，两者可叠加。
