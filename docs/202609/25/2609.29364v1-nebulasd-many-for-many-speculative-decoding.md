## 摘要
推测解码通过使用轻量级草稿模型提出候选 token，并由目标模型并行验证，从而加速大语言模型（LLM）推理。然而，草稿与验证具有不同的服务特性，并偏好不同的批配置，使得在并发工作负载下固定的草稿-目标耦合效率低下。现有分布式设计可以在物理上分离这两个阶段，但往往保留请求或批次亲和性，阻碍其容量被全局共享。我们提出 NebulaSD，一种多对多（many-for-many，即 M-for-N）推测解码系统，将草稿 worker 和目标 worker 组织为可独立调度的资源池，并从共享请求池中动态重构阶段特定的批次。这种动态重分配消除了固定的 worker 局部性，要求请求状态能够在新选择的 worker 上可用，且不引入迁移停顿。NebulaSD 通过 worker 触发的批次重构以及与模型执行重叠的异步 KV 状态准备来应对这一挑战。我们从系统与扩展性两个视角评估 NebulaSD，表明在四 GPU 部署中，动态池化将请求轮次处理速率相较物理分离基线提升 50.4%，相较共置执行提升 72.6%，同时大幅提高有效 GPU 利用率。基于性能剖析的仿真进一步表明，在理想化状态迁移下，计算侧容量可近似成比例扩展。

## Abstract
Speculative decoding accelerates Large Language Model (LLM) inference by using a lightweight draft model to propose candidate tokens for parallel verification by a target model. Drafting and verification, however, exhibit different service characteristics and favor different batch configurations, making fixed draft-target coupling inefficient under concurrent workloads. Existing distributed designs can physically separate the two stages, but often retain request or batch affinities that prevent their capacities from being shared globally. We present NebulaSD, a many-for-many, or M-for-N, speculative decoding system that organizes draft and target workers into independently schedulable resource pools and dynamically reconstructs stage-specific batches from shared request pools. Such dynamic reassignment removes fixed worker locality, requiring request states to be made available at newly selected workers without introducing migration stalls. NebulaSD addresses this challenge through worker-triggered batch reconstruction and asynchronous KV-state preparation overlapped with model execution. We evaluate NebulaSD from both system and scaling perspectives, showing that dynamic pooling improves request-round processing rate by 50.4% over a physically disaggregated baseline and 72.6% over co-located execution on a four-GPU deployment while substantially increasing effective GPU utilization. Profile-driven simulations further show approximately proportional compute-side capacity scaling under idealized state movement.

## 1. 核心问题与研究动机

- **背景**：LLM 自回归解码延迟高、服务成本大。推测解码（Speculative Decoding）通过轻量草稿模型提议多个候选 token，再由目标模型并行验证，从而在一次目标前向中提交多个 token，显著加速推理。
- **核心矛盾**：草稿（drafting）与验证（verification）具有不同的服务特性，且偏好不同的批配置。论文图 1 显示：
  - Qwen3-8B 的前向延迟在 batch=512 时急剧上升，而 Qwen3-1.7B 几乎不变；
  - 两个模型随 batch 增大表现出不同的 GPU 资源需求（DRAM 带宽压力 vs. Tensor Core 饱和）。
- **固定耦合的低效**：现有系统仍以固定的请求/批次亲和性组织两个阶段，导致某一阶段的空闲容量无法共享给其他配对中成为瓶颈的请求，系统有效服务率受限于每个配对的局部慢阶段。
- **已有分布式方案的不足**：物理分离（disaggregation）虽可分别供给两个阶段，但现有设计聚焦于异构部署、边缘协作、验证侧批处理或远程草稿，未将草稿与目标 worker 同时暴露为**全局可调度资源池**，仍保留跨阶段批次亲和性。
- **新挑战**：动态重分配请求会打破固定 worker 的局部性；自回归生成中每个请求携带不断增长的 KV cache，状态必须在新目标 worker 上可用，否则迁移会落入执行关键路径。

## 2. 方法论

### 2.1 核心思想
- 提出 **M-for-N（many-for-many）** 架构：M 个草稿 worker 与 N 个目标 worker 组成两个**独立供给、全局可调度**的资源池。
- 移除固定请求-worker 亲和性与跨阶段批次亲和性；每个阶段维护共享请求池，worker 从池中动态重建自己的批次。
- 通过 **worker 触发的批次重建** 与 **异步 KV 状态准备**，将状态迁移尽量移出执行关键路径。

### 2.2 系统模型与关键公式
- 阶段依赖：`draft^q_r ≺ target^q_r ≺ draft^{q+1}_r`，即前一阶段输出必须先于下一阶段计算，但 worker 分配与状态准备可提前规划。
- 批次执行时间 `bT_s(B) = φ_s(z_B)`，阶段服务率 `μ_s(B) = |B| / bT_s(B)`。
- 系统稳态速率上限：`μ_sys ≤ min{μ_D, μ_T}`，说明两池需按各自服务能力独立供给。
- **完成时间预测**：若前驱未完成，用 `b_e_r = t_start + φ_¯s(z)` 预测；否则用观测值 `e_r`。
- **状态就绪时间**：`b_k(B,w) = max_{r∈B} b_k_r(w)`。
- **最早可开始时间**：
  `b_S(B,w) = max{ b_a_w, max_{r∈B} b_e_r, b_k(B,w) }`，同时捕捉 worker 可用、前驱输出就绪、KV 状态就绪三个条件。
- **服务约束的批次重建**：定义服务准入界 `b_d_r(w) = max{ b_e_r + g_s, b_S({r},w) } + Δ_s`，其中 `g_s` 为目标服务间隔，`Δ_s` 为允许的批形成额外延迟。批次 B 可被 worker w 接纳当且仅当：
  - `|B| ≤ B_max`
  - `Fit(B,w) = 1`（物理容量约束）
  - `b_S(B,w) ≤ min_{r∈B} b_d_r(w)`（不因批形成过度延迟任何请求）
- **算法流程**（Algorithm 1）：过滤并预测就绪时间 → 按前驱就绪、等待时间、时序兼容性排序 → 贪心构造满足约束的批次 → 冻结/预留批次并发出 PREPARE → 当 `INPUT READY ∧ KV READY ∧ WORKER READY` 时执行 RUN。

### 2.3 关键实现技术
- **持久化 HostKV**：主机端常驻草稿与目标 KV 状态，使用预注册 pinned-memory arena 与稳定偏移，避免重复分配与注册。
- **增量 KV 回写**：只异步写回尚未持久化的有效 KV 后缀；迁移成本估计为 `bT_s,wb = ΔQ_s(B)·bKV_s / β_s,D2H`，`bT_s,in = Q_s(B)·bKV_s / β_s,H2D`。
- **双缓冲 GPU KV Bank**：每个 worker 维护两个 bank，状态机为 `FREE → FILLING → READY → COMPUTING → EXPORTING → FREE`，实现 `COMPUTE_{k+1} ∥ D2H_k`、`COMPUTE_k ∥ H2D_{k+1}`。
- **共享内存控制平面**：固定布局的共享内存表 + 单写者协议 + 序列号快照读，避免互斥锁与 RPC 序列化。
- **进程隔离 worker 运行时**：控制进程、执行进程、DMA 进程分离，避免 CPU 调度延迟、Python 运行时、拷贝完成处理干扰模型执行。
- **有界 H2D 提交**：将大 H2D 计划切分为 32 MiB 块，限制单 bank 的 H2D 队列长度，减少与另一 bank D2H 的跨 bank 队头阻塞。
- **事件驱动调度**：将“规划路径”（触发批次重建）与“推进路径”（就绪检查）分离，支持在 standby bank 上提前规划下一批次。

## 6. 主要结论与发现

- **性能提升**：四 GPU 上，NebulaSD 请求轮处理速率达 1914.83 rounds/s，较 Native Distributed（1273.35）提升 **50.4%**，较 Co-located（1109.37）提升 **72.6%**。
- **利用率提升**：时间加权 SM 活跃度从 Co-located 的 30.1%、Native Distributed 的 29.4% 提升至 **47.3%**；Draft/Target 平均计算间隔分别从 114.96/24.03 ms 降至 **4.38/4.45 ms**。
- **性能来源**：提升主要来自动态批重建填充执行气泡，而非简单增大 batch——NebulaSD 的草稿平均 batch（89.24）反而小于 Native Distributed（128），目标 batch（31.32）与计算时间基本持平。
- **请求侧权衡**：同等四 GPU 预算下，每请求计算服务比例从 Co-located 的 97.9%、Native Distributed 的 56.6% 降至 44.0%，即系统服务更多并发请求但单请求获得算力比例下降。
- **扩展性**：理想仿真显示，当按服务能力比例配置两池时，聚合容量随系统规模近似成比例增长；152 GPU 配置达 86.06% SM 活跃度与 99.61% 请求服务比例，处理 139.3K rounds/s。
- **并发依赖性**：低并发下固定配对已足够，NebulaSD 收益有限；高并发下共享请求
