## 摘要
投机解码通过使用轻量级草稿模型提出候选 token，并由目标模型并行验证，从而加速大语言模型（LLM）推理。然而，起草与验证表现出不同的服务特征，并偏好不同的批配置，这使得固定的草稿-目标耦合在并发工作负载下效率低下。现有分布式设计可以在物理上分离这两个阶段，但往往保留请求或批的亲和性，使其容量无法全局共享。我们提出 NebulaSD，一个多对多（即 M 对 N）的投机解码系统，它将草稿工作器和目标工作器组织为可独立调度的资源池，并从共享请求池中动态重构阶段特定的批。这种动态重新分配消除了固定的工作器局部性，要求请求状态在新选定的工作器上可用，且不引入迁移停顿。NebulaSD 通过工作器触发的批重构以及与模型执行重叠的异步 KV 状态准备来应对这一挑战。我们从系统和扩展性两个角度评估 NebulaSD，结果表明，在四 GPU 部署中，动态池化相比物理解聚基线将请求轮次处理速率提高了 50.4%，相比同址执行提高了 72.6%，同时显著提高了有效 GPU 利用率。基于性能画像的仿真进一步表明，在理想化状态迁移下，计算侧容量能够近似按比例扩展。

## Abstract
Speculative decoding accelerates Large Language Model (LLM) inference by using a lightweight draft model to propose candidate tokens for parallel verification by a target model. Drafting and verification, however, exhibit different service characteristics and favor different batch configurations, making fixed draft-target coupling inefficient under concurrent workloads. Existing distributed designs can physically separate the two stages, but often retain request or batch affinities that prevent their capacities from being shared globally. We present NebulaSD, a many-for-many, or M-for-N, speculative decoding system that organizes draft and target workers into independently schedulable resource pools and dynamically reconstructs stage-specific batches from shared request pools. Such dynamic reassignment removes fixed worker locality, requiring request states to be made available at newly selected workers without introducing migration stalls. NebulaSD addresses this challenge through worker-triggered batch reconstruction and asynchronous KV-state preparation overlapped with model execution. We evaluate NebulaSD from both system and scaling perspectives, showing that dynamic pooling improves request-round processing rate by 50.4% over a physically disaggregated baseline and 72.6% over co-located execution on a four-GPU deployment while substantially increasing effective GPU utilization. Profile-driven simulations further show approximately proportional compute-side capacity scaling under idealized state movement.

## 一、核心问题与研究动机

- **背景**：LLM 自回归解码延迟高、服务成本大。投机解码（Speculative Decoding）通过轻量草稿模型提议多个候选 token，再由目标模型单次前向并行验证并提交多个 token，从而加速生成。
- **核心矛盾**：起草（drafting）与验证（verification）具有**不同的服务特征**：
  - 草稿模型小（如 Qwen3-1.7B），批大小增大时延迟几乎不变（至 512 批次仍约 16–18ms）；
  - 目标模型大（如 Qwen3-8B），批次到 512 时延迟急剧上升。
  - 两者对 GPU 资源的需求（Kernel DRAM% 与 Tensor%）也随批次变化而分化。
- **结构性低效**：现有系统多以**固定的一对一草稿-目标配对**或固定请求/批次亲和性组织执行，某一阶段的空闲容量无法共享给另一阶段成为瓶颈的请求，导致有效服务速率被每对中较慢阶段限制，容量被局部化浪费。
- **已有工作不足**：近期分布式投机解码（Disaggregated SD、SLED、WISP、DSD、SPECTRE）虽实现物理分离，但主要面向异构部署、边缘协同、远端草稿或验证调度，**未将草稿与目标 worker 都暴露为全局可调度的资源池**，仍保留跨阶段或 worker 级别的亲和性。
- **关键挑战**：一旦允许请求在 worker 间动态重分配，KV 缓存状态必须在新目标 worker 上就绪，否则迁移会直接落在执行关键路径上；而迁移过早又可能引入无谓传输并干扰前台计算。

## 二、方法论

### 核心思想
将 **M 个草稿 worker 与 N 个目标 worker 组织为两个独立供给、全局可调度的资源池**，从共享请求池中动态重建各阶段的 worker 本地批次，解除请求-worker 亲和性与跨阶段批次亲和性，使两阶段容量可独立匹配各自负载。

### 系统模型（第 4 节）
- 请求 r 在草稿阶段与目标阶段分别维护逻辑执行状态 $S_r^D$、$S_r^T$，不永久绑定任何 worker。
- 执行依赖关系：$draft_q^r \prec target_q^r \prec draft_{q+1}^r$。
- 批次执行时间画像 $bT_s(B)=\phi_s(z_B)$，阶段服务速率 $\mu_s(B)=|B|/bT_s(B)$。
- 系统稳态速率受慢阶段限制：$\mu_{sys} \le \min\{\mu_D, \mu_T\}$。

### 关键机制
1. **重叠式批次规划与状态准备**：worker 可在前驱阶段完成前，利用预测完成时间提前选择请求并准备 KV 状态，实现「目标计算 ∥ 草稿状态准备」「草稿计算 ∥ 目标状态准备」的对称流水线。
2. **Worker 触发的批重建（Algorithm 1）**：
   - 预测请求前驱完成时间 $\hat{e}_r = t_{start} + \phi_{\bar s}(z)$；
   - 预测 KV 就绪时间 $\hat{k}_r(w)$，批次 KV 就绪 $\hat{k}(B,w)=\max_{r\in B}\hat{k}_r(w)$；
   - 最早预测开始时间 $\hat{S}(B,w)=\max\{\hat{a}_w, \max_{r\in B}\hat{e}_r, \hat{k}(B,w)\}$；
   - 服务准入界 $\hat{d}_r(w)=\max\{\hat{e}_r+g_s, \hat{S}(\{r\},w)\}+\Delta_s$；
   - 准入条件：$|B|\le B_{max}$、$Fit(B,w)=1$、$\hat{S}(B,w)\le\min_{r\in B}\hat{d}_r(w)$；
   - 按服务紧迫度与时序兼容性排序，**贪心构造**批次以避免在线穷举子集优化。
3. **PREPARE → RUN 两阶段协议**：预测时间决定「准备什么」，运行时事件（INPUT READY ∧ KV READY ∧ WORKER READY）决定「何时执行」。

### 实现要点（第 5 节）
- **Persistent HostKV**：主机端常驻 KV 存储，draft/target 分区，稳定偏移与元数据（有效长度、位置、版本），避免重复分配与注册。
- **增量写回**：仅异步写回未持久化的 KV 后缀，保留前缀，估计迁移成本 $\hat{T}_{s,wb}$、$\hat{T}_{s,in}$。
- **双缓冲 GPU KV Bank**：FREE→FILLING→READY→COMPUTING→EXPORTING→FREE，实现 `COMPUTE_{k+1} ∥ D2H_k`、`COMPUTE_k ∥ H2D_{k+1}`。
- **共享内存控制平面**：单写者分区表、序列化发布协议、eventfd 门铃、无锁读取。
- **进程隔离 worker 运行时**：control / execution / DMA 三进程分离，避免控制面与拷贝完成处理干扰延迟敏感的 GPU 提交路径。
- **有界 H2D 提交**：默认 32 MiB 分块，减少跨 bank 队头阻塞。

## 六、主要结论与发现

1. **动态池化显著提升吞吐**：四 GPU 下请求轮处理速率达 1914.83 rounds/s，较 Native Distributed（1273.35）提升 **50.4%**，较 Co-located（1109.37）提升 **72.6%**。
2. **利用率提升**：时间加权 SM 活跃度从 30.1%（Co-located）和 29.4%（Native Distributed）提升至 **47.3%**；草稿/目标计算间隔分别从 114.96/24.03 ms 降至 4.38/4.45 ms。
3. **收益来自填充执行气泡而非增大批次**：NebulaSD 草稿平均批（89.24）反而小于 Native Distributed（128），目标批与单批计算时间相近。
4. **代价是每请求服务比例下降**：同预算下从 97.9%/56.6% 降至 44.0%，但可通过扩大 worker 池与匹配两阶段容量缓解。
5. **计算侧近似线性扩展**：在理想状态迁移下，按服务容量比例供给的池化架构容量随系统规模近似成比例增长。
6. **并发决定工作点**：低并发时固定配对已足够（Native Distributed 在 256 请求时略优）；高并发（384/512）下 NebulaSD 分别领先约 25% 和 49%。
7. **KV 状态增长削弱收益**：max gen 从 128 增至 512 时，相对提升从 62.1% 降至 7.1%，主因是主机-设备带宽受限导致迁移暴露。
8. **迁移干扰可控**：进程隔离可将 1024 MiB D2H 造成的目标模型延迟增幅从 46.13% 降至 3.07%，说明主要开销来自传输调度与前台回读阻塞，而非 kernel 本身变慢。
9. **对模型规模与深度稳健**：换用 Qwen3-1.7B 草稿或 depth 3/5，仍保持 1.45×–1.72× 的优势。

## 七、优点

- **抽象层次清晰**：将分布式投机解码从「设备间通信问题」重构为「两个独立 worker 池的全局调度问题」，问题定位明确。
- **系统设计完整**：调度策略（worker 触发批重建、服务准入界）+ 运行时机制（HostKV、双 bank、进程隔离、有界 H2D）配套，且给出 PREPARE→RUN 的工程落地协议。
- **调度与执行解耦**：区分「规划路径」与「进度路径」，避免冻结批次被反复重建，控制面开销可控。
- **实验双轨互补**：真实四卡测量运行时表现，理想仿真隔离调度潜力，结论相互印证。
- **敏感性覆盖广**：KV 长度、深度、调度参数、并发、草稿规模、系统规模均有测试，并明确说明不依赖窄域调参。
- **对负面结果的诚实处理**：明确报告每请求服务比例下降、低并发时无优势、512 token 时收益收窄、Native Distributed 显存不足等。

## 八、不足与局限

- **硬件规模有限**：真实实验仅
