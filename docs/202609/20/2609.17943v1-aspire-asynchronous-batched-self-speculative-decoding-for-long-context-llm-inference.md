## 摘要
长上下文LLM推理受限于注意力机制，其重复的KV缓存读取使解码成为内存瓶颈。自推测解码通过使用稀疏注意力起草token并用全注意力验证它们来缓解这一问题，但现有的批处理方法仍保持同步：一个批次中的所有请求共享单一的起草-验证调度，尽管最优起草长度在不同请求之间差异很大，并且会在每个请求内部动态变化。我们提出ASPIRE，一个基于三个组件构建的非同步批处理自推测解码框架。首先，统一的混合前向传播允许起草请求和验证请求共存于同一次批处理前向传播中，从而无需全局的起草-验证阶段。其次，轻量级在线推测调度器使用每个请求的接受率估计和批次感知成本模型，让每个请求独立选择何时进行验证。第三，起草内刷新层在起草期间于单个指定层执行全注意力，在每个起草步骤更新稀疏上下文，以减少起草期间的陈旧性。在三个模型和五个推理与长上下文基准上，ASPIRE相较于自回归基线在解码吞吐量上实现了$1.70$-$4.58\times$的加速，并且相较于最强的先前自推测基线将平均加速比提高了约$27\%$。

## Abstract
Long-context LLM inference is bottlenecked by attention, whose repeated KV-cache reads make decoding memory-bound. Self-speculative decoding alleviates this by drafting tokens with sparse attention and verifying them with full attention, but existing batched methods remain synchronized: all requests in a batch share a single draft-verify schedule, even though the optimal draft length varies widely across requests and changes dynamically within each request. We propose ASPIRE, a non-synchronized batched self-speculative decoding framework built on three components. First, a unified mixed forward allows drafting and verifying requests to coexist in the same batched forward pass, removing the need for global draft-verify phases. Second, a lightweight online speculation scheduler uses per-request acceptance-rate estimates and a batch-aware cost model to let each request independently choose when to verify. Third, an intra-draft refresh layer performs full attention at a single designated layer during drafting, updating the sparse context at every draft step to reduce staleness during drafting. Across three models and five reasoning and long-context benchmarks, ASPIRE achieves $1.70$-$4.58\times$ speedup in decoding throughput over autoregressive baselines and improves average speedup by approximately $27\%$ over the strongest prior self-speculative baselines.

# ASPIRE 论文中文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **长上下文推理的瓶颈**：Transformer 解码由两个组件主导——MLP 层以权重访问为主、偏计算受限；自注意力依赖上下文长度、偏内存受限。批处理可以摊销 MLP 的权重加载（使 GEMV 近似变为 GEMM），但**注意力无法跨请求摊销**，因为每个请求有独立的 KV 缓存，每生成一个 token 都要读取其全部历史上下文的 KV。
- **自推测解码的应对思路**：用稀疏注意力起草多个 token，再用全注意力一次性验证，把昂贵的全 KV 读取摊销到多个被接受的 token 上，因而在长上下文场景下极具吸引力。
- **现有方法的关键缺陷**：
  - **同步批处理**：MagicDec、Vegas 等方法让整批请求共享同一套“起草-验证”节奏。但最优草稿长度在不同请求之间差异巨大（实测每请求平均接受长度从 2.56 到 20.00，均值 11.51），且在同一请求内部也随生成进程剧烈波动。同步批处理导致部分请求“草稿不足”、部分请求“草稿过度”。
  - **草稿上下文陈旧**：Vegas 在起草期间固定部分 KV 上下文，仅在验证后刷新；随着起草推进，上下文越来越陈旧，限制草稿长度与质量。
- **论文含义**：提出 ASPIRE——面向长上下文 LLM 推理的**非同步批处理自推测解码框架**，把调度粒度下沉到单个请求，同时用轻量刷新机制缓解草稿陈旧。

## 2. 方法论

### 核心思想
让同一批次内的不同请求在同一前向传播中处于不同的推测状态（起草或验证），由每个请求的在线调度器独立决定何时验证，并通过单个刷新层在起草期间更新稀疏上下文。

### 关键技术细节

- **4.1 统一混合前向（Unified Mixed Forward）**
  - 每一步把活跃请求分为验证集 $V_t$ 与起草集 $D_t$。
  - 起草请求用稀疏注意力（稀疏集 $S_i$）解码 1 个 token；验证请求用全注意力解码 $d_i+1$ 个 token。
  - 因两种模式共享同一目标模型权重与 MLP 计算，仅注意力上下文与解码长度不同，故可合并为单次批处理前向，保留 MLP 的批处理收益，同时允许注意力保持请求特化。
  - 消除了全局起草/验证阶段，实现请求级异步。

- **4.2 推测调度器（Speculation Scheduler）**
  - **目标草稿长度 $\gamma_i$**：基于 Leviathan 等人的期望推测效率目标，令 $c_i = T^{\text{draft}}_i / T^{\text{verify}}_i$ 为起草-验证成本比，则
    $$\gamma_i = \arg\max_{\gamma \in \{0,\dots,d_{\max}\}} \frac{(1-\alpha_i^{\gamma+1})/(1-\alpha_i)}{1 + c_i\gamma}$$
    即最大化预测的“单位时间提交 token 数”。
  - **接受率估计 $\alpha_i$**：由验证结果在线更新，$\hat\alpha_i = a_i/\min(a_i+1, d_i)$（部分接受视为 $a_i$ 次成功 + 1 次失败），再指数平滑 $\alpha_i \leftarrow \omega\alpha_i + (1-\omega)\hat\alpha_i$；初始用先验 $\alpha_0$，且必须先起草至少 $\gamma_{\text{init}}$ 个 token 才能验证。
  - **批次感知成本比**：拟合一个三步运行时模型
    $$\tau_t = \beta_{\text{model}} + \beta_{\text{mlp}}\cdot n_t + \beta_{\text{attn}}\cdot\left(\sum_{j\in D_t}|S_j| + \sum_{j\in V_t}\ell_j\right)$$
    其中 $n_t$ 为总前向 token 数（MLP 计算受限），注意力项与读取的 KV 长度线性相关（内存受限）。在“全批均为请求 $i$ 副本”的均匀批近似下推出 $T^{\text{draft}}_i$、$T^{\text{verify}}_i$，从而得到 $c_i$，并随 $d_i$、$\ell_i$、$|S_i|$ 在线重算。
  - **决策规则**：$d_i \ge \gamma_i$ 或 $d_i \ge d_{\max}$ 则验证，否则继续起草。

- **4.3 起草内上下文刷新（Intra-Draft Refresh）**
  - 依据观察：注意力图在**跨层**上的相关性比**跨时间**更稳定。设计在指定的**刷新层 $\ell_r$**（默认倒数第二层 $N-2$）执行全注意力，捕获其注意力 logits 用于为下一步选取稀疏 KV 页面。
  - **稀疏集选择**：对 logits 做 online softmax 得权重 $A^{\text{src}}_{i,t,h}(u)$，定义 token 重要性 $r_{i,t}(u)=\max_h A^{\text{src}}_{i,t,h}(u)$；在 paged KV 上按页打分 $s_{i,t}(P)=\sum_{u\in P} r_{i,t}(u)$。
  - **预算**：$k_i = \max(k_{\min}, \lceil \rho P_i\rceil)$，其中最近 $L$ 页恒被保留以保证局部连续性，其余槽位按分数取 top。
  - 验证阶段对首尾两个验证 token 的页分数取平均。
  - 只增加每起草步一次全注意力层，开销极小（实测约 1% 周期时间）。

## 6. 主要结论与发现

- **加速效果**：ASPIRE 在全部模型与工作负载上均优于自回归基线，短上下文推理最高 2.12×/1.86×/1.80×（三个模型），长上下文最高 4.58×/2.75×/2.66×；随上下文从 16K 增至 80K，加速比进一步增大，说明其特别适合内存受限的长上下文解码。
- **平均加速**：整体平均加速比 3.34×（Qwen3-1.7B）、2.08×（Qwen3-8B）、2.14×（DS-Llama-8B）；较最强先前自推测基线（多为 Vegas）平均提升约 27%。
- **消融结论**：
  - 混合执行 + 调度器相对 ASPIRE-Fixed 的增益在短上下文很小，但在长上下文明显扩大（如 Qwen3-8B 从 2.22× 提升到 2.75× @ LB-v2[80k-100k]），说明固定草稿长度的同步推测随上下文增长愈发次优。
  - 相比 ASPIRE-FSM，完整调度器在依赖“接受率 + 批次代价”联合决策时更优，且在模型与工作负载间表现更一致。
- **刷新机制**：无刷新时接受率随草稿长度增长骤降（$\gamma=10$ 时降至 60.3%），有刷新时保持 76.6%，**缩小 16.4 个百分点差距**，证明起草内刷新有效缓解上下文陈旧。
- **调度器余量**：与事后 Oracle 相比，ASPIRE 差距 4.7%–20.2%（均值 10.4%），长上下文三格平均 8.5%，说明仍有但有限的提升空间。
- **刷新层位置**：接受率在 $N/4$ 到 $N-2$ 之间高而平坦，两端（层 0 与最后一层）明显下降；$N-2$ 稳健且无需逐模型调参。
- **精确性**：ASPIRE 构造上精确，稀疏注意力只影响候选 token 的生成，所有 token 均经全注意力验证；端到端质量对比确认实现正确。
- **张量并行**：时序模型函数形式可迁移，但系数需按部署配置重新校准；复用 TP=1 系数在 LB[16k-18k] 上会使加速比从 2.07× 降至 1.51×（不影响正确性）。

## 7. 优点

- **问题洞察精准**：通过实证研究量化了草稿长度在请求间与请求内的双重异质性，直接指向同步批处理这一结构性瓶颈。
- **方法设计自洽**：统一混合前向让起草与验证共享同一目标模型前向，既打破同步约束又保留批处理效率，是较优雅的工程-算法协同设计。
- **调度器轻量且在线**：仅需接受率估计与三步代价模型，无需训练额外网络，可在线逐步决策。
- **刷新机制开销极小**：仅增加每起草步一层全注意力（约 1% 周期时间），却带来显著的接受率提升与更长有效草稿。
- **实验体系完整**：主实验 + 多组消融 + Oracle 上界 + 质量验证 + 超参/页大小/刷新层位置/TP 鲁棒性扫描，覆盖较全面，结论可信。
- **强调精确性**：明确属于标准精确推测解码设定，验证保证输出分布与目标模型一致，并给出端到端质量校验。
- **实用导向**：给出了部署所需的一次性校准要求与超参默认值，并讨论了与 vLLM 等生产引擎集成的未来方向。

## 8. 不足与局限

- **质量评估覆盖有限**：端到端输出质量仅在 Qwen3-8B 与 8 个 LongBench-v1 任务（1,460 样本）上验证，未覆盖全部三个模型与长上下文基准（LongBench-v2、AIME、CodeElo）。
- **短上下文收益有限且非一致最优**：在 AIME25 上 Vegas 略优、CodeElo 上 ASPIRE-Fixed 最优，说明混合执行 + 调度器的收益高度依赖内存受限程度；短上下文场景下组件可能带来额外复杂度却收益甚微。
- **与生产引擎集成未完成**：与通用连续批处理引擎（尤其 chunked prefill 场景）的融合被明确列为未来工作，当前评估环境较受控。
- **校准依赖**：代价模型系数需针对每个部署配置（如不同 TP 度）重新 profiling；陈旧系数虽不影响正确性，但会显著降低吞吐（LB[16k-18k] 上 2.07× → 1.51×）。
- **Oracle 余量**：与事后最优调度仍有约 10.4% 平均差距，调度策略仍有优化空间；同时调度器对超参（$\omega$、$\alpha_0$）的扫描显示非单调行为，run-to-run 波动与生成长度差异会干扰估计收敛。
- **实验规模与硬件单一**：主实验在单张 H100 上完成，未展示大规模多节点/高并发服务场景下的表现；批大小取“能装下的最大值”，不同方法批大小不完全一致，可能引入一定比较偏差。
- **未涉及训练侧或跨硬件泛化**：未讨论在其他加速器（如非 NVIDIA 平台）上的可移植性，也未评估极长上下文（>100k）的行为。
