## 摘要
投机解码可加速 rollout 生成，而 rollout 生成主导了强化学习（RL）后训练的开销。在线协同训练可进一步提升草稿模型的准确率，从而带来更大的加速。然而，将该方法扩展到长上下文大模型上的协同训练面临两个障碍：(1) 标准因果上下文并行（CP）实现不支持分支注意力；(2) 目标特征跨越流水线并行（PP）阶段。我们通过一个面向大规模在线草稿协同训练的端到端系统同时解决这两个问题。对于 CP，我们扩展了打包且负载均衡的 zigzag 环形注意力，将各 rank 本地的分支注意力与因果主序列注意力合并。对于 PP，TapChannel 通过单独路径跨阶段传输中间目标特征，且不影响流水线调度。实验表明，协同训练的草稿模型能够紧密跟踪策略基线，同时在高达 122B 的模型规模上带来显著的 rollout 和端到端加速。我们的 CP 设计在 256K token 下实现了强扩展性，并相比先前工作显著节省内存；我们的 PP 传输仅带来适度开销。代码见 https://github.com/NVIDIA-NeMo/RL/issues/3698。

## Abstract
Speculative decoding accelerates rollout generation, which dominates the cost of reinforcement learning (RL) post-training. Online co-training can further increase the draft's accuracy, yielding greater speedups. However, scaling this approach to co-training on large models with long contexts poses two obstacles: (1) branch attention is unsupported by standard causal context-parallel (CP) implementations, and (2) target features span across pipeline-parallel (PP) stages. We address both with an end-to-end system for large-scale online draft co-training. For CP, we extend packed, load-balanced zigzag ring attention by merging rank-local branch attention with causal main-sequence attention. For PP, TapChannel transports intermediate target features across stages via a separate path, leaving the pipeline schedule unaffected. Experiments demonstrate that co-trained drafts closely track the policy baseline while delivering substantial rollout and end-to-end speedups across model scales up to 122B. Our CP design achieves strong scaling at 256K tokens with significant memory savings over prior work, and our PP transport incurs modest overhead. Code can be found at https://github.com/NVIDIA-NeMo/RL/issues/3698.

# 论文总结：大规模长上下文 RL 后训练中面向投机解码的在线草稿协同训练

## 1. 核心问题与整体含义

- **研究背景**：强化学习（RL）后训练已成为构建推理型与智能体型大语言模型（LLM）的标准范式，而 RL 后训练的墙钟时间主要由 **rollout 生成**主导。
- **投机解码（Speculative Decoding, SD）** 通过“小模型起草 + 大模型并行验证”加速自回归生成，且不改变输出分布。近期 RL 框架已将 SD 集成到 rollout 引擎，并证明 rollout 加速可转化为端到端训练加速。
- **在线协同训练**：随 RL 策略演化持续训练草稿模型，可延长接受长度、获得更大加速。但扩展到**大模型、长上下文**场景面临两个系统级障碍：
  1. **分支注意力不被标准因果上下文并行（CP）支持**：EAGLE-3（TTT 多步自回归）、DFlash（块扩散）、DSpark（并行骨干 + Markov 头）等先进草稿引入分支结构注意力，标准因果 CP 无法处理。
  2. **目标特征跨越流水线并行（PP）阶段**：草稿模型依赖目标模型中间层隐藏状态，而这些特征可能位于远离草稿的 PP 阶段，标准 PP 仅连接相邻阶段。
- **整体含义**：论文主张**不修改目标模型的并行拓扑**，而是围绕现有 CP/PP 配置适配系统，使在线草稿协同训练在大规模长上下文 RL 后训练中变得可行。

## 2. 方法论

### 2.1 核心思想

- 保持策略模型的 CP/PP 并行布局不变，通过两个机制扩展系统能力：
  - **CP 侧**：将草稿分支注意力分解为“因果主序列组件”与“rank 本地分支组件”，分别计算后合并。
  - **PP 侧**：引入 **TapChannel**，以独立于流水线调度的侧路径传输中间目标特征。

### 2.2 在线协同训练目标

- 策略参数 θ，草稿参数 φ；草稿在相同 rollout token 上训练，目标特征 $H_\theta(x)$ 施加 stop-gradient：
  $$L(\theta, \phi) = L_{RL}(\theta) + \lambda L_{draft}(\phi; x, sg(H_\theta(x)))$$
- 草稿模型作为子模块挂载在策略的**最后一个 PP 阶段**，与策略联合更新。

### 2.3 CP 下的分支注意力

- **打包 zigzag-ring 注意力**：主序列因果前缀按 zigzag 方式分片到各 CP rank；分支本地 KV 保留在拥有分支锚点的 rank 上。
- **两阶段合并**：每个分支 query 分别关注两个键集——主序列因果前缀（跨 rank 环形传递）与分支本地键（本地计算），再用标准 online-softmax 归并：
  $$\ell = \log(e^{\ell_m} + e^{\ell_b}), \quad O = e^{\ell_m - \ell} O_m + e^{\ell_b - \ell} O_b$$
  其中 $(O_m, \ell_m)$ 与 $(O_b, \ell_b)$ 分别对应主序列与分支部分的注意力输出与 log-sum-exp。
- **统一支持三类草稿架构**：EAGLE-3（TTT 每个草稿位置形成分支）、DFlash（块扩散一次生成整块）、DSpark（并行骨干 + Markov 头恢复块内因果依赖）。
- **通信成本**：CP 度为 C、主序列 N 个 token 均分时，每 rank 出站量为 $V_{fwd}^{CP} = 2(C-1)\frac{N}{C}d_{kv}b$，**与分支数量/深度无关**；反向重放同一 K/V 环，无额外分支相关流量。
- **重叠策略**：ring-step 粒度上，下一步通信在当前注意力计算前发出、在下一步边界等待；暴露开销 $E(r)_{CP} = \max(t_{comm}^{(r)}, t_{attn}^{(r)})$。长上下文下注意力二次增长、通信线性增长，重叠余量更大。

### 2.4 PP 下的 TapChannel

- **问题**：产生 tap 的层跨多个 PP 阶段，草稿仅位于最后阶段；标准 PP 只能相邻阶段通信。
- **设计**：在草稿阶段为每个源维护**预分配 mailbox 槽位**；源阶段完成某 microbatch 的策略前向后写入槽位，草稿阶段在同一 microbatch 前向前读取。
- **同步机制**：每个槽位带序列戳（sequence stamp），源与草稿在每次写/读时递增。同节点源（CUDA IPC）由草稿读取后清除戳；跨节点源（专用 NCCL communicator + GPUDirect RDMA）用戳做顺序保证，缓冲区复用由有界 in-flight 发送和接收端 CUDA 事件管理。
- **通信成本**：每 microbatch 特征载荷 $V_{Tap} = bn \sum_{s \in S} d_s$，每个特征只直传一次，与 PP 跳数无关。
- **残余会合延迟**：$E(m)_{Tap} = \max_{s \in S} \max(\tau_{s,m}, \Delta_{s,m})$，仅超出流水线松弛窗口的部分产生可见开销。

## 6. 主要结论与发现

- **策略学习保持**：协同训练的草稿模型紧密跟踪 baseline 的 reward、验证准确率和训练–推理 KL 散度，说明投机解码与在线协同训练**不破坏 RL 学习轨迹**，保持 on-policy 假设。
