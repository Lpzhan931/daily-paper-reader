## 摘要
推测解码通过使用轻量级草稿模型提出候选 token，并由目标模型并行验证，从而加速大语言模型（LLM）推理。然而，起草与验证具有不同的服务特性，并偏好不同的批配置，使得在并发工作负载下固定的草稿-目标耦合效率低下。现有分布式设计可以在物理上分离这两个阶段，但往往保留请求或批的亲和性，导致其容量无法全局共享。我们提出 NebulaSD，一种多对多（M-for-N）推测解码系统，它将草稿 worker 和目标 worker 组织成可独立调度的资源池，并从共享请求池中动态重构阶段特定的批。这种动态重分配消除了固定的 worker 局部性，要求在新选定的 worker 上可获取请求状态，同时不引入迁移停顿。NebulaSD 通过 worker 触发的批重构以及与模型执行重叠的异步 KV 状态准备来应对这一挑战。我们从系统和扩展两个视角评估 NebulaSD，结果表明，在四 GPU 部署上，动态池化将请求轮次处理速率较物理分离基线提高 50.4%，较同址执行提高 72.6%，同时大幅提高有效 GPU 利用率。基于性能剖析的仿真进一步表明，在理想化状态迁移下，计算侧容量近似成比例扩展。

## Abstract
Speculative decoding accelerates Large Language Model (LLM) inference by using a lightweight draft model to propose candidate tokens for parallel verification by a target model. Drafting and verification, however, exhibit different service characteristics and favor different batch configurations, making fixed draft-target coupling inefficient under concurrent workloads. Existing distributed designs can physically separate the two stages, but often retain request or batch affinities that prevent their capacities from being shared globally. We present NebulaSD, a many-for-many, or M-for-N, speculative decoding system that organizes draft and target workers into independently schedulable resource pools and dynamically reconstructs stage-specific batches from shared request pools. Such dynamic reassignment removes fixed worker locality, requiring request states to be made available at newly selected workers without introducing migration stalls. NebulaSD addresses this challenge through worker-triggered batch reconstruction and asynchronous KV-state preparation overlapped with model execution. We evaluate NebulaSD from both system and scaling perspectives, showing that dynamic pooling improves request-round processing rate by 50.4% over a physically disaggregated baseline and 72.6% over co-located execution on a four-GPU deployment while substantially increasing effective GPU utilization. Profile-driven simulations further show approximately proportional compute-side capacity scaling under idealized state movement.

- **背景**：大语言模型（LLM）的自回归解码延迟高、服务成本大。推测解码（Speculative Decoding）通过轻量级草稿模型一次提议多个候选 token，再由目标模型并行验证，从而在单次目标前向中提交多个 token，显著加速生成。

- **现有方案的不足**：已有的分布式推测解码（如 Disaggregated SD、SLED、WISP、DSD、SPECTRE）虽在物理上分离了草稿与验证，但主要面向异构部署、边缘-云协作、验证端批处理或远程草稿，**仍保留请求或批的亲和性**，未将两侧 worker 暴露为可全局调度的资源池。

- **整体含义**：论文提出 **NebulaSD**，将推测解码视为一种 **M-for-N（多对多）服务问题**，把草稿与目标 worker 组织为两个可独立调度、全局共享的资源池，并协调批重建与状态准备，使动态重分配不成为新瓶颈。

## 二、方法论：核心思想与关键技术

### 2.1 核心思想

- **M-for-N 架构**：M 个草稿 worker（池 D）与 N 个目标 worker（池 T）作为两个独立配置、独立调度的资源池；请求不再永久绑定到某个 worker 或某个草稿-目标对。
- **共享请求池 + 动态批重建**：每个阶段维护共享请求池，worker 在每次投机迭代中从池中动态重建阶段专属批次；同一阶段内请求可跨 worker 迁移，跨阶段不要求批次成员保持一致。
- **对称流水线**：草稿计算与目标侧状态准备重叠，目标计算与草稿侧状态准备重叠；稳态下在 TARGET_q、DRAFT_{q+1}、TARGET_{q+1} 之间交替。

### 2.2 关键建模与公式（文字说明）

- **执行依赖**：draft^q_r ≺ target^q_r ≺ draft^{q+1}_r，即前一阶段输出必须先于下一阶段计算，但 worker 分配与 KV 准备可提前规划。
- **阶段服务率**：μs(B) = |B| / bTs(B)，其中 bTs(B) = φs(zB) 为剖析得到的批执行时间，zB 汇总批大小、上下文长度、提议深度等负载特征。
- **系统稳态上限**：μsys ≤ min{μD, μT}，即整体吞吐受较慢阶段限制，这正是不应固定配对的根本原因。
- **预测完成时间**：若前驱未完成，用 ber = tstart + φ_s̄(z) 预测；若已完成则用观测值 er。记 eer 为可用的前驱完成时间。
- **状态就绪时间**：bk(B, w) = max_{r∈B} bkr(w)，bkr(w) 为请求 r 的 KV 状态在 worker w 上可用的预测时间。
- **最早预测开始时间**：bS(B, w) = max{ baw（worker 可用时间）, max_{r∈B} eer（前驱就绪）, bk(B, w)（KV 就绪） }，三条件联合决定未来执行。
- **服务准入界**：bdr(w) = max{ eer + gs, bS({r}, w) } + Δs，其中 gs 为阶段目标服务间隔，Δs 为允许的额外批形成松弛。
- **批可采纳条件**：|B| ≤ Bmax 且 Fit(B, w) = 1 且 bS(B, w) ≤ min_{r∈B} bdr(w)，即批大小、物理容量、批形成延迟三重约束。
- **算法流程（Algorithm 1）**：过滤候选请求 → 按前驱就绪度、等待时间、时间兼容性排序 → 取前 Bmax 个 → 贪心逐个加入满足可采纳条件的请求 → 冻结并预留批、发出 PREPARE(B, w) → 当 INPUT READY ∧ KV READY ∧ WORKER READY 时执行 RUN。

### 2.3 关键技术细节

- **持久化 HostKV**：为草稿和目标模型各维护主机端常驻 KV 区域（预注册 pinned memory arena，固定偏移），避免反复分配/注册/重打包；记录有效序列长度、位置、版本等轻量元数据。
- **增量 KV 写回**：仅异步写回尚未持久化的有效 KV 后缀，保留不变前缀，减少 D2H 流量；迁移成本估计为 bTs,wb(B) = ΔQs(B)·bKV,s / βs,D2H，bTs,in(B) = Qs(B)·bKV,s / βs,H2D。
- **双缓冲 GPU KV Bank**：每个 worker 维护两个预分配 bank，状态机为 FREE → FILLING → READY → COMPUTING → EXPORTING → FREE；一个 bank 计算时另一个可准备下一批，实现 COMPUTE_{k+1} ∥ D2H_k 与 COMPUTE_k ∥ H2D_{k+1}。
- **进程隔离 worker 运行时**：控制进程（状态机与命令处理）、执行进程（模型与 GPU KV）、DMA 进程（KV 拷贝提交与完成），避免控制面/拷贝完成处理与模型共享延迟敏感的 CPU 路径。
- **有界 H2D 提交**：将大 H2D 计划切分为默认 32 MiB 的块，限制单 bank 的 H2D 排队，避免阻塞另一 bank 的 D2H，减少跨 bank 队头阻塞。
- **事件驱动调度**：仅在候选请求集或准备容量变化时触发规划；区分"规划路径"（重建批）与"进展路径"（仅检查就绪），避免重复调度开销。
- **PREPARE → RUN 两阶段协议**：PREPARE 冻结批成员、目标 worker、bank 身份与预期状态版本；RUN 仅在前驱结果发布、KV 版本就绪、worker 恢复计算能力后执行。

## 三、实验设计

### 3.1 实验场景与基准

- **真实系统（4 GPU）**：4 张 RTX 4090，草稿模型 Qwen3-0.6B，目标模型 Qwen3-8B，推测深度 4；512 个请求同时到达，最大生成长度 128 token，目标最大批大小固定为 32。
- **主指标**：请求轮处理速率（每秒完成的推测轮数，每轮 = 一次草稿 + 一次目标验证）。
- **对比方法**：
  - **Co-located**：每 GPU 各放一个草稿实例 D 和一个目标实例 T，传统耦合执行；
  - **Native Distributed**：物理分离为 2D + 2T，草稿批上限 128，但保留跨阶段批亲和性；
  - **NebulaSD**：同样 2D + 2T 资源配置，额外启用共享请求池、worker 触发批重建、跨 worker 状态迁移、提前状态准备；
  - **Simulation NebulaSD**：理想化模拟器，用于隔离调度潜力与运行时开销。
- **大规模仿真**：19 / 24 / 38 / 48 / 76 / 96 / 152 / 192 GPU 的多种 D:T 配比（如 3D+16T、6D+32T、8D+40T、12D+64T、16D+80T、24D+128T、32D+160T），对比 Co-located 基线。

### 3.2 敏感性实验

- **KV 状态增长**：最大生成长度 128 / 256 / 512 token。
- **提议深度**：3 / 4 / 5。
- **调度器参数**：服务间隔 gs 联合缩放 0.5× / 1.0× / 1.5×；松弛 Δs = 0 / 30 / 60 ms。
- **请求并发**：同时提交 256 / 384 / 512 个请求。
- **草稿模型规模**：Qwen3-0.6B vs Qwen3-1.7B（目标仍为 Qwen3-8B）。
- **KV 迁移干扰微基准**：单 GPU 上 H2D / D2H 传输 2 MiB – 1024 MiB，对比同进程 vs 独立进程提交。
