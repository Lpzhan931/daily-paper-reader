## 摘要
大型语言模型的单流自回归解码受限于内存带宽：每个生成的token需要对目标模型执行一次完整的前向传播，且连续传播无法并行化。推测性解码重构了这一计算过程：一个小型草稿模型自回归地提出K个token，目标模型在一个批处理前向传播中对所有token进行评分，而拒绝采样规则可证明地保持了目标模型的输出分布。我们提出了一种从头实现的、设备无关（CUDA/MPS/CPU）的实现，并在消费级Apple Silicon笔记本电脑上，针对五种草稿/目标后端配置进行了实证研究。在三个层面验证了分布等价性，最终对每种方法约9200个真实模型token进行了双样本检验（χ²=162.5，自由度=200，p=0.976），并确保了精确的贪婪序列一致性。最佳配置在K=6时达到实测1.61倍的墙钟加速，接受率从K=1时的69.7%下降至最优点的37.8%，而五种配置中有三种出现了减速，原因要么是草稿模型无法超越小型目标模型的速度，要么是量化后的Metal后端串行执行“并行”验证——我们对此效应进行了分离和量化。这些失败与成功同样具有启发性：推测性解码仅在验证真正批量并行且草稿/目标延迟差距真实存在时才能带来收益。

## Abstract
Single-stream autoregressive decoding of large language models is bound by memory bandwidth: each generated token requires one full forward pass through the target model, and successive passes cannot be parallelized. Speculative decoding restructures this computation: a small draft model proposes $K$ tokens autoregressively, the target model scores all of them in one batched pass, and a rejection-sampling rule provably preserves the target model's output distribution. We present a from-scratch, device-agnostic (CUDA/MPS/CPU) implementation and an empirical study across five draft/target backend configurations on a consumer Apple-silicon laptop. Distribution equivalence is verified at three levels, culminating in a two-sample test over roughly 9,200 real-model tokens per method ($χ^2 = 162.5$, dof $= 200$, $p = 0.976$) and exact greedy-sequence agreement. The best configuration reaches a measured $1.61\times$ wall-clock speedup at $K=6$, on an acceptance profile declining from 69.7% at $K=1$ to 37.8% at the optimum, while three of five configurations decelerate, either because the draft fails to out-speed a small target or because the quantized Metal backend executes "parallel" verification serially, an effect we isolate and quantify. The failures are as instructive as the successes: speculative decoding pays off only when verification is genuinely batch-parallel and the draft/target latency gap is real.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：大型语言模型（LLM）的单流自回归解码受限于内存带宽——每个生成的 token 需要一次完整的前向传播，且连续步骤无法并行化。推测解码（Speculative Decoding）通过引入小型草稿模型并行验证多个候选 token，理论上可无损保持目标模型输出分布并加速推理，但在消费级硬件上实际加速效果受到系统实现因素的严重制约。
- **整体含义**：本文揭示了推测解码在消费级硬件（Apple Silicon）上的真实表现，指出“无损”是数学保证，但“加速”是系统属性，并非必然。当验证未真正并行或草稿模型速度不够快时，推测解码可能反而导致减速。

## 2. 方法论

### 2.1 核心思想
- 草稿模型自回归生成 K 个候选 token（保留每个位置的概率分布 \(q_i\)），目标模型一次性批量验证所有 K 个位置（获得分布 \(p_1 \dots p_K\) 及一个免费奖励分布 \(p_{K+1}\)），通过拒绝采样规则决定接受或拒绝部分草稿，最后从调整分布中重采样，保证输出分布与直接使用目标模型完全一致。

### 2.2 关键技术细节
- **拒绝采样规则**（式 1）：\(r_i \sim U(0,1)\)，接受 \(x_i\) 当且仅当 \(r_i < \min(1, \frac{p_i(x_i)}{q_i(x_i)})\)。
- **调整分布**（式 2）：在第一个拒绝位置 a+1，从 \(p' \propto \max(0, p_{a+1} - q_{a+1})\) 中采样一个 token 代替拒绝位置及后续草稿。
- **免费奖励 token**：如果所有 K 个草稿都被接受，则额外从 \(p_{K+1}\) 中采样一个 token（该分布已计算）。
- **实现**：设备无关架构（CUDA/MPS/CPU），采样数学在 CPU float32 上执行以保证可复现性；支持 Hugging Face Transformers（fp16）和 llama.cpp GGUF（4/8bit）后端混合使用；单一 tokenizer 保证词表一致性。

### 2.3 伪代码流程（文字描述）
1. 草稿阶段：使用草稿模型自回归生成 K 个 token，记录每个位置的完整分布 \(q_i\)。
2. 验证阶段：目标模型一次性对所有 K 个新位置进行前向传播（利用已存 KV cache），得到 \(K+1\) 个分布 \(p_1 \dots p_{K+1}\)。
3. 接受/拒绝行走：遍历 \(i=1..K\)，对每个草稿 token 检查接受条件，找到第一个被拒绝的位置 a+1。
4. 如果所有 K 个草稿都被接受，则输出奖励 token（来自 \(p_{K+1}\)），共 \(K+1\) 个 token。
5. 否则，在拒绝位置 a+1 从调整分布中重采样一个 token，丢弃该位置以后的草稿，输出接受的 a 个草稿 + 重采样 token。
6. 截断两个模型的 KV cache 到接受长度，重复直到结束。

## 6. 主要结论与发现

1. **最佳加速**：配置 `mixed_3b`（0.5B q8_0 draft → 3B fp16 MPS target）在 \(K=6\) 时达到 **1.61×** 墙钟加速；\(K=2\)–6 形成平台（1.52–1.61×）。
2. **三种配置减速**：`all_gguf`（0.50×）、`stretch_7b`（0.52×）、`primary`（0.33×）均减速。原因有二：
   - 草稿慢于目标：在 MPS 上运行 Transformers fp16 的 0.5B 草稿耗时 18.0 ms/步，超过 llama.cpp 1.5B 目标整个步的 13.6 ms。
   - 验证串行化：llama.cpp Metal 后端在批次 2–7 时执行逐位置矩阵-向量乘，验证耗时线性增长（而非恒定），彻底破坏了推测解码的并行假设。
3. **分布等价性验证**：三层验证均通过（统计 p=0.976、合成分布 KL<3.5e-4、贪婪序列比特一致），证明实现保持输出分布。
4. **接受率随位置衰减**：位置 1 接受率 ~70%，位置 4 降至 ~36% 或更低（取决于草稿/目标质量差距），导致边际收益递减。
5. **采样开销极小**：CPU float32 采样数学仅占墙钟的 2.2%，验证了设计合理性。
6. **最优 K** 位于接受率降至高 30% 的区域（\(K=6\) 时 37.8%），超过一定阈值后吞吐量急剧下降。

## 7. 优点

- **设备无关实现**：代码可在 CUDA、MPS、CPU 上不加修改运行，并支持跨后端混合使用，增强了通用性和可复现性。
- **严格正确性验证**：从单个采样规则的统计测试到完整解码器的分布等价性检验，再到真实模型的 χ² 检验，三层验证保证了实现无误。
- **消除减速原因**：通过延迟分解和针对 verifier 批处理行为微基准测试，清晰量化了减速的根本原因（框架开销和验证串行化），这些发现对于其他硬件和实现具有指导意义。
- **消融实验完备**：K 扫描、位置接受率、延迟分解、峰值内存等指标全面，能够解释速度变化机制。
- **开源可复现**：代码、提示集、工具、结果 JSON 均公开，并提供 Colab 脚本以便他人扩展 8B 类结果。
- **结论实用**：明确指出推测解码并非万能，需要满足两个条件才能加速（验证真正并行、草稿大幅快于目标），为工程师提供了明确部署指南。

## 8. 不足与局限

- **硬件单一**：所有结果仅来自一台 Apple M3 笔记本，无法推广到其他消费级硬件（如 Intel/AMD CPU、NVIDIA GPU 的量化推理）或服务器类硬件。
- **模型范围窄**：仅使用 Qwen2.5 家族，未测试不同架构（如 Llama、Mistral）或跨家族配对，接受率和延迟特性可能不同。
- **实验规模小**：K 扫描仅 8 条提示，标准差大；分布等价性检验仅 ~9,200 token，统计功效有限（无法排除小概率偏差）。建议更多提示和更长生成序列。
- **缺乏重复运行**：主要基准每个配置只运行一次（28 提示平均），未报告多次重复间的波动，仅报告单次运行的标准差（跨提示），无法评估运行间方差。
- **温度固定**：所有加速实验在 T=0.8 下，实际应用可能需要不同温度或采样式解码（如 top-p），对接受率和加速比有影响。
- **量化 Metal 后端 logits 非批次不变性**：导致贪婪测试无法在原始后端子运行，必须使用 CPU fp32 后端验证，暗示量化后端可能存在数值不稳定性。
- **缺少 8B 类结果**：提供的 Colab 脚本未执行，缺少更大规模模型的验证，削弱了结论对内存约束设备（18GB）上更大模型的适用性。
- **峰值内存为高水位上限**：非精确每个配置的内存使用，只能作为上界比较。
- **仅 batch size 1**：结果对服务场景批量推理无指导意义。
