## 摘要
投机解码通过并行验证来自 Draft 模型的多个 token，减少了顺序的 Target 模型调用。然而，KV Cache 的增长在 GPU 内存受限时限制了长上下文服务。将 KV 卸载到 CPU 内存可缓解这一压力。然而，现有卸载方案会在注意力计算前恢复完整 KV 历史，未能充分利用一个验证轮次内跨查询 KV 共享带来的收益。现有并行投机解码方法还忽略了：当受内存带宽限制的 Target 验证等待历史 KV 时，GPU 计算能力处于闲置状态。我们提出 SpecStream，一种投机解码系统，它无需等待完整 KV 历史恢复便开始验证，并利用 KV 传输期间的计算气泡在同一组 GPU 上并发生成草稿。它仅卸载 Target 已提交的历史，使候选回滚保留在 GPU 本地。每个流式传输的 KV 分块服务于该轮次中的所有查询，并通过在线 softmax 保持完整注意力。Target 优先级调度在资源限制下控制 Draft 的并发执行，以约束其对 Target 验证的干扰。实验表明，在有限 GPU 内存下，SpecStream 在支持更多并发请求的同时，保持与 SGLang 投机解码接近的任务质量。在不同数据集上，对于 Qwen3 和 InternLM2.5，它相比卸载基线分别实现了平均 1.41$\times$ 和 1.32$\times$ 的吞吐量加速。与在独立 Target 和 Draft GPU 上进行的并行投机解码相比，SpecStream 将每 GPU 输出吞吐量平均提高了 55.4%。

## Abstract
Speculative decoding reduces sequential Target model calls by verifying multiple tokens from the Draft model in parallel. Yet KV Cache growth limits long-context serving under constrained GPU memory. Offloading KV to CPU memory relieves this pressure. However, existing offloading schemes restore the full KV history before attention and fail to fully exploit the benefits of KV sharing across queries within a verification round. Existing parallel speculative decoding methods also overlook idle GPU compute capacity while memory-bandwidth-bound Target verification waits for historical KV. We present SpecStream, a speculative decoding system that begins verification without waiting for the full KV history to be restored and exploits compute bubbles during KV transfers for concurrent drafting on the same GPUs. It offloads only Target-committed history, keeping candidate rollback local to the GPUs. Each streamed KV chunk serves all queries in the round, with online softmax preserving full attention. Target-priority scheduling controls Draft concurrent execution under resource limits to constrain interference with Target verification. Experiments show that SpecStream maintains task quality close to SGLang speculative decoding while supporting more concurrent requests under limited GPU memory. Across different datasets, it achieves average throughput speedups of 1.41$\times$ and 1.32$\times$ over the offloading baseline for Qwen3 and InternLM2.5, respectively. Compared with parallel speculative decoding on separate Target and Draft GPUs, SpecStream improves output throughput per GPU by an average of 55.4%.

## 一、核心问题与研究动机

- **背景**：长上下文 LLM 服务中，KV Cache 随序列增长持续膨胀，成为 GPU 显存的核心瓶颈。投机解码（Speculative Decoding）虽能通过 Draft 模型并行生成候选、Target 模型一次前向验证多个 token，从而减少顺序 Target 调用，但**并未消除每一轮验证对历史 KV 的依赖**，反而因需同时容纳 Target/Draft 两套权重与 KV、候选状态及执行缓冲，使显存压力更早触顶。

- **现有卸载方案的缺陷**：
  - 将 KV 卸载到 CPU 内存虽可缓解显存压力，但现有方案（如 SD+Offload）**必须在注意力计算前恢复当前层完整的 KV 历史**，传输时间随上下文长度增长并进入 Target 验证的关键路径。
  - 未区分 KV 的"已提交（committed）"与"未验证候选（speculative）"生命周期，可能传输并维护后续被拒绝候选的 KV。
  - 未利用**同一验证轮次内多个查询共享同一份已提交历史 KV** 的特性来摊销传输成本。

- **并行投机解码的缺陷**：MineDraft、SPECTRE、SwiftSpec 等通过跨 GPU 并行或流水线调度隐藏草稿延迟，但**未利用 Target 等待历史 KV 传输时 GPU 计算单元的空闲"气泡"**，且依赖额外 GPU 资源。

- **核心洞察**：
  - 一轮验证中的 q 个查询因果可见性不同，但共享相同的已提交历史，一次历史拷贝可服务整组查询。
  - 等待历史 KV 时复制引擎在搬运数据、但计算单元空闲，此时 Draft 模型仍有候选可生成，二者资源需求互补。
  - Draft 资源分配需权衡：分配过少延长草稿延迟，分配过多则干扰 Target 验证（论文图 1 显示吞吐呈先升后降趋势）。

## 二、方法论：SpecStream 系统

SpecStream 在 SGLang 上实现，包含三个协同组件，核心思想是**围绕投机解码完整步骤的状态与访问特征，联合设计历史管理、流式计算与共享 GPU 调度**。

### 2.1 提交感知的无回滚 KV 分层（Commit-Aware Rollback-Free KV Tiering）

- **状态三划分**：将 Target KV Cache 按 token 位置划分为：
  - **Sealed History** `[0, H)`：已迁移完成的已提交历史，位于 CPU；
  - **Active Tail** `[H, C_r)`：近期已提交 KV，位于 GPU；
  - **Speculative Frontier** `[C_r, L_r)`：候选 KV，位于 GPU。
  - 满足 `0 ≤ H ≤ C_r ≤ L_r`。

- **关键机制**：迁移资格以 Target **提交边界 `C_r`** 为约束，CPU 只保存不可撤销的已提交前缀；候选的接受/拒绝/回收全在 GPU 本地完成，因此**历史迁移与候选回滚操作于互不相交的状态区间**（`[C'_r, L_r) ∩ [0, H) = ∅`），无需 CPU 侧清理或跨设备回滚。

- **批量迁移**：保留目标长度为 `T` 的 Active Tail，以粒度 `g` 批量迁移，迁移终点为
  `E = max(H, g·⌊max(0, C_r − T)/g⌋)`；
  仅当 `E > H` 时异步迁移 `[H, E)`，拷贝确认完成后才推进边界并回收 GPU 空间。

### 2.2 面向多查询验证的 KV 流式传输（KV Streaming for Multi-Query Verification）

- **分块 + 查询组共享**：将当前层 Sealed History 沿 token 位置切成 J 个连续块。第 j 块 `(K_j, V_j)` 到达 GPU 后，用整组查询矩阵 `Q ∈ R^{q×d_h}` 计算 `S_j = Q K_j^T / √d_h`。**一块只传输一次即可服务本轮所有 q 个查询**，处理完即可让缓冲区接收下一块，无需等待当前层完整历史恢复。

- **在线 softmax 保证精确全注意力**：维护每查询每头的三元累加器 `(m, ℓ, a)`（分别为已处理位置的最大分数、相对最大值的指数和、加权值之和），初值 `(−∞, 0, 0)`。每块局部状态：
  `m_j = max(S_j)`，`ℓ_j = Σ_k e^{S_{j,k} − m_j}`，`a_j = Σ_k e^{S_{j,k} − m_j} V_{j,k}`；
  合并时统一到公共最大值 `m' = max(m, m_j)`，缩放因子 `α = e^{m−m'}`、`β = e^{m_j−m'}`，更新 `ℓ' = αℓ + βℓ_j`、`a' = αa + βa_j`。处理完全部 CPU 历史后再处理 GPU 常驻的 Active Tail 与 Speculative Frontier（后者需按绝对位置施加因果掩码）。最终输出 `O = a/ℓ`，与一次性全历史 softmax 在实数算术下等价。

- **流水线与预取**：使用两个 GPU 暂存缓冲与独立的传输/计算流，缓冲 A 计算块 j 时缓冲 B 接收块 j+1；相邻块组成传输批以减少拷贝提交、同步与 kernel 启动开销；当前层缓冲释放后预取下一层历史。

- **Cohort 批处理**：在当前调度批内，将层、验证宽度、数据类型、KV 头数、头维度、块大小兼容的请求聚合为 Cohort，按组准备数据并用批量注意力 kernel 执行，同时保留各请求独立的 KV 索引、绝对位置与在线 softmax 状态。

- **I/O 感知的动态验证宽度**：控制器以"每个有效输出 token 的估计时间"为目标，`q* = arg min_{q∈Q} ( T̂_round(q) / Û(q) )`，基于近期历史传输、验证、草稿生成与拒绝纠正成本及实际提交 token 数进行估计；记录不足时通过有限初始采样收集，且仅在估计收益超过切换阈值时改变 q。

### 2.3 Target 优先的 GPU 内协同执行（Target-Priority Intra-GPU Co-Execution）

- **Draft 计算资源分配**：利用 NVIDIA MPS 让 Target 与 Draft 在独立进程并发执行；通过 **TPC（Texture Processing Cluster）掩码**限制 Draft 的计算 kernel 只运行在指定 TPC 子集上（不隔离 L2/带宽，需运行时控制争用）。离线扫描不同 TPC 分配下的性能，记录 Draft 单步时间 `t_D(x, n)` 与 Target 延迟增幅 `ΔT(x, n) = [T^co_T(x,n) − T^alone_T(x)] / T^alone_T(x)`，据此选定默认分配 `n_0`（实验中为 34 TPC/GPU）。

- **Target 优先调度**：运行时结合前一轮观测更新估计。仅当同时满足
  `Δ̂T(x, n_0) ≤ ε_T`（Target 延迟增幅在可接受预算内）且 `t̂_D(x, n_0) + δ ≤ Ŝ`（含安全裕度的一步 Draft 能装入剩余窗口）时，才提交一次并发步骤。

- **单 token 准入与反馈**：每次只准入一个完整 Draft 前向（单 token），以限制不可立即撤销的在途工作；调度指令携带请求/投机轮次标识、执行序号、TPC 分配与最晚启动时间 `t_latest = t_0 + Ŝ − t̂_D − δ`，过期或不匹配的指令不执行；Draft 完成后返回 ACK，Target 据此决定是否继续调度下一步。若延迟超预算则停止提交新步骤，待已启动计算完成后恢复 Target 独占执行。
