## 摘要
推测解码通过并行验证来自草稿（Draft）模型的多个词元，减少目标（Target）模型的串行调用次数。然而，KV缓存增长限制了受限GPU内存下的长上下文服务。将KV卸载到CPU内存可缓解这一压力。然而，现有卸载方案在注意力计算前恢复完整的KV历史，未能充分利用单轮验证中跨查询KV共享带来的收益。现有并行推测解码方法还忽视了当受内存带宽限制的目标验证等待历史KV时闲置的GPU计算能力。我们提出SpecStream，一种推测解码系统，其无需等待完整KV历史恢复即可开始验证，并利用KV传输期间的计算气泡在同一批GPU上进行并发草稿生成。它仅卸载目标模型已确认的历史，将候选回滚保留在GPU本地。每个流式传输的KV块服务于该轮中的所有查询，并通过在线softmax保持完整注意力。目标优先调度在资源限制下控制草稿的并发执行，以约束其对目标验证的干扰。实验表明，SpecStream在任务质量上接近SGLang推测解码，同时在有限的GPU内存下支持更多并发请求。在不同数据集上，对于Qwen3和InternLM2.5，其吞吐量相较卸载基线分别平均加速1.41倍和1.32倍。与在独立的目标和草稿GPU上进行并行推测解码相比，SpecStream将每GPU输出吞吐量平均提升55.4%。

## Abstract
Speculative decoding reduces sequential Target model calls by verifying multiple tokens from the Draft model in parallel. Yet KV Cache growth limits long-context serving under constrained GPU memory. Offloading KV to CPU memory relieves this pressure. However, existing offloading schemes restore the full KV history before attention and fail to fully exploit the benefits of KV sharing across queries within a verification round. Existing parallel speculative decoding methods also overlook idle GPU compute capacity while memory-bandwidth-bound Target verification waits for historical KV. We present SpecStream, a speculative decoding system that begins verification without waiting for the full KV history to be restored and exploits compute bubbles during KV transfers for concurrent drafting on the same GPUs. It offloads only Target-committed history, keeping candidate rollback local to the GPUs. Each streamed KV chunk serves all queries in the round, with online softmax preserving full attention. Target-priority scheduling controls Draft concurrent execution under resource limits to constrain interference with Target verification. Experiments show that SpecStream maintains task quality close to SGLang speculative decoding while supporting more concurrent requests under limited GPU memory. Across different datasets, it achieves average throughput speedups of 1.41$\times$ and 1.32$\times$ over the offloading baseline for Qwen3 and InternLM2.5, respectively. Compared with parallel speculative decoding on separate Target and Draft GPUs, SpecStream improves output throughput per GPU by an average of 55.4%.

# 论文总结：Resource-Efficient Speculative Decoding for Long-Context LLM Serving（SpecStream）

## 1. 核心问题与整体含义

- **背景**：长上下文 LLM 服务中，自回归解码逐 token 生成，KV Cache 随序列增长持续占用 GPU 显存，成为核心瓶颈。推测解码（Speculative Decoding）通过 Draft 模型一次生成多个候选 token、Target 模型一次前向并行验证，减少了 Target 的串行调用次数，但并未消除每一轮验证对历史 KV 状态的依赖。
- **核心矛盾**：
  - 显存受限下，将 KV 卸载到 CPU 内存可缓解压力，但现有卸载方案（如 SD+Offload）必须**先恢复当前层完整的 KV 历史**才能开始注意力计算，传输时间随上下文增长而延长，落在 Target 验证的关键路径上。
  - 一轮 Target 验证中的多个查询**共享同一份已提交历史 KV**，但现有方案未充分利用这一跨查询共享来摊销传输成本。
  - Target 验证受内存带宽限制、等待历史 KV 时，GPU 计算单元处于空闲状态，而现有并行推测解码方案（如 SPECTRE、MineDraft、SwiftSpec）多依赖**额外 GPU** 或在独立资源上重叠 Draft，未能利用同一批 GPU 上的计算气泡。
- **整体含义**：论文提出 SpecStream，围绕推测解码中 KV Cache 的**状态特征与访问特征**联合设计历史管理、流式计算与共享 GPU 调度，在有限显存下同时提升并发能力与吞吐效率。

## 2. 方法论

### 2.1 核心思想
- 以 Target 的**提交边界（commit boundary）**约束历史迁移，仅卸载不可回滚的已提交 KV，候选回滚完全留在 GPU 本地；验证无需等待完整 KV 恢复即可开始，并利用 KV 传输等待期间的空闲算力并发推进 Draft。

### 2.2 关键技术细节

**（1）提交感知的无回滚 KV 分层（Commit-Aware Rollback-Free KV Tiering）**

- 将每个请求的 Target KV Cache 划分为三个区域（满足 0 ≤ H ≤ Cr ≤ Lr）：
  - **Sealed History** `[0, H)`：已完成迁移的已提交历史，存放于 CPU。
  - **Active Tail** `[H, Cr)`：最近提交的 KV，保留在 GPU。
  - **Speculative Frontier** `[Cr, Lr)`：候选 KV，留在 GPU 等待验证。
- 迁移终点由公式决定：`E = max(H, g·⌊max(0, Cr − T)/g⌋)`，其中 `T` 为 Active Tail 目标长度、`g` 为迁移粒度。仅当 `E > H` 时异步迁移 `[H, E)`，完成后才推进历史边界并回收 GPU 空间。
- 验证结束后，接受候选并入 Active Tail，后缀 `[C′r, Lr)` 在 GPU 上释放。由于 `H ≤ Cr ≤ C′r` 恒成立，回滚区间与 CPU 历史区间不相交，**无需 CPU 副本清理或跨设备回滚**。

**（2）多查询验证的 KV 流式传输（KV Streaming for Multi-Query Verification）**

- **分块共享**：将当前层的 Sealed History 沿 token 位置切分为 J 个连续块，每个块到达 GPU 后以整组查询 `Q ∈ R^{q×dh}` 计算注意力得分 `Sj = QKjᵀ/√dh`，一次传输服务本轮全部 q 个查询。
- **在线 softmax 保持完整因果注意力**：为每个查询和注意力头维护三元累加器 `(m, ℓ, a)`，初始为 `(−∞, 0, 0)`。对每个到达块计算局部状态 `(mj, ℓj, aj)`，再以 `m′ = max(m, mj)`、`α = e^{m−m′}`、`β = e^{mj−m′}` 做重缩放合并：`ℓ′ = αℓ + βℓj`，`a′ = αa + βaj`。处理完全部 CPU 历史块后继续处理 GPU 上的 Active Tail 与 Speculative Frontier（需按绝对位置施加因果掩码），最终输出 `O = a/ℓ`。该分块归约在实数运算下**等价于一次性完整 softmax**，仅改变 KV 到达与归约顺序。
- **流水线与预取**：双 GPU 暂存缓冲区 + 独立传输/计算流，边算块 j 边传块 j+1；相邻块打包为传输批次；当前层缓冲区释放后预取下一层历史 KV。
- **Cohort 批处理**：将当前调度批次中兼容的任务（相同模型层、验证宽度、数据类型、KV 头数、头维度、块大小）归组，以批量注意力核执行，各请求保留独立 KV 索引、绝对位置与在线 softmax 状态。
- **I/O 感知的动态验证宽度**：按估计的"每个有效输出 token 的耗时"选择宽度，`q* = arg min_{q∈Q} (T̂round(q)/Û(q))`，Q = {2,4,6,8}；利用近期历史传输、验证、Draft 生成、拒绝纠正成本与提交 token 数估计；记录不足时有限采样；仅当收益超过切换阈值才改变宽度。

**（3）Target 优先的 GPU 内协同执行（Target-Priority Intra-GPU Co-Execution）**

- 使用 NVIDIA MPS 让 Target 与 Draft 在不同 CUDA 进程中并发；以 **TPC 粒度掩码**限制 Draft 的计算资源（TPC 为含多个 SM 的硬件簇），Target 保留全部计算资源；但 L2 与内存带宽仍共享，需运行时控制竞争。
- **离线测量**：扫描不同 TPC 分配下 Draft 单步时间 `tD(x,n)` 与 Target 验证延迟增幅 `ΔT(x,n) = [T^co_T(x,n) − T^alone_T(x)]/T^alone_T(x)`，选出默认分配 `n0`（实验中为每 GPU 34 TPC）。
- **运行时准入条件**：仅当 `Δ̂T(x,n0) ≤ εT`（延迟增幅在可接受范围）且 `t̂D(x,n0) + δ ≤ Ŝ`（单步时长加安全裕度能放入剩余窗口）时，才提交一个 Draft 步骤。
- **单 token 准入与反馈**：每次只允许一个完整 Draft 前向（生成一个 token），携带请求/轮次标识、执行序号、TPC 分配与最晚开始时间；Draft 完成后返回 ACK，Target 再决定是否继续调度；若动态宽度、批次或上下文变化导致干扰超预算，则停止新步骤、恢复 Target 独占执行。

## 6. 主要结论与发现

- **任务质量**：SpecStream 与 SGLang SD 的最大得分差异仅 0.1988 个百分点，说明分块归约只带来微小浮点累积顺序扰动，不损害输出质量。
- **吞吐提升**：在三个数据集上，SpecStream 相比 TriForce 在 Qwen3 和 InternLM2.5 上平均加速 1.41× 和 1.32×；相比 SD+Offload 为 1.44× 和 1.62×。
- **共享 GPU 优势**：相比 3-GPU 的 SPECTRE+Offload，SpecStream 平均吞吐为 1.036×，但按 GPU 数量归一化后每 GPU 输出吞吐平均提升 **55.4%**，即用 2 块 GPU 达到接近 3 块 GPU 的吞吐。
- **显存受限下的并发能力**：随并发请求增加，AR 与 SGLang SD 因显存上限吞吐饱和，SpecStream 通过将历史 KV 移至 CPU 保持 GPU 容量，32 并发时 CPU KV 峰值达每 GPU 45.50 / 49.50 GiB；Qwen3 因累计 H2D 流量更大（7.79 TiB vs 3.29 TiB）吞吐恢复较弱。
- **消融结论**：流式访问（K2）贡献最大增益（16K 输入下 Qwen3 +83.2%、InternLM2.5 +117.1%）；预取（K3）再提升约 3%–15.6%；动态宽度（K4）收益依赖场景（Qwen3 +8.5%~16.0%，InternLM2.5 −1.2%~+9.6%）；Cohort（K5）在 4–16 并发下提升 4.6%–17.3%，单请求几乎无收益。
- **动态宽度的关键洞察**：平均接受长度增加并不必然带来吞吐提升（如 InternLM2.5 八请求下接受长度 3.64→6.22，吞吐反降 1.2%），必须权衡额外计算与有效输出。
- **调度结论**：Target 优先并发执行相比串行提升 9.9%–43.6%（Qwen3）与 2.7%–31.7%（InternLM2.5），单请求时增益最大；TPC 扫描显示 30–38 TPC 为高效区间，34 TPC 为最优默认值。

- **工程实现完整**：双缓冲、跨层预取、Cohort 批处理、MPS + TPC 掩码、单 token 准入与 ACK 反馈等机制配套齐全，并在 SGLang 上落地。
- **公平意识**：对比额外 GPU 方案时按 GPU 数量归一化，消融实验使用相同 KV 预算与输入。
- **动态宽度控制器**：以"每有效输出 token 成本"而非单纯接受长度为目标，避免盲目增大验证宽度。

## 8. 不足与局限

- **Draft KV 未卸载**：当前实现将完整 Draft KV Cache 保留在 GPU 上，随并发增长占用越来越多显存，成为新的容量约束；论文明确指出连续 Draft 步骤之间缺乏多查询复用机会，直接套用同一卸载路径会反复拉取历史 KV、拉长候选生成等待，这是未来工作方向。
