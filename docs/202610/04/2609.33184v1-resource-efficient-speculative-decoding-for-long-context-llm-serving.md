## 摘要
推测解码通过并行验证来自草稿模型的多个 token，减少了顺序调用目标模型的次数。然而，KV 缓存的增长限制了 GPU 内存受限条件下的长上下文服务。将 KV 卸载到 CPU 内存可缓解这一压力。但是，现有卸载方案在注意力计算前恢复完整的 KV 历史，未能充分利用验证轮次内跨查询的 KV 共享优势。现有并行推测解码方法也忽视了在受内存带宽限制的目标验证等待历史 KV 时闲置的 GPU 计算能力。我们提出 SpecStream，一种推测解码系统，它无需等待完整 KV 历史恢复便开始验证，并利用 KV 传输期间的计算气泡在同一批 GPU 上并发进行草稿生成。它仅卸载目标模型已提交的历史，将候选回滚保留在 GPU 本地。每个流式传输的 KV 块服务于该轮次中的所有查询，并通过在线 softmax 保持完整注意力。目标优先调度在资源限制下控制草稿模型的并发执行，以约束其对目标验证的干扰。实验表明，SpecStream 在有限 GPU 内存下支持更多并发请求，同时保持任务质量接近 SGLang 推测解码。在不同数据集上，针对 Qwen3 和 InternLM2.5，它分别相比卸载基线取得平均 1.41 倍和 1.32 倍的吞吐量加速。与在独立目标 GPU 和草稿 GPU 上运行的并行推测解码相比，SpecStream 将每 GPU 输出吞吐量平均提高 55.4%。

## Abstract
Speculative decoding reduces sequential Target model calls by verifying multiple tokens from the Draft model in parallel. Yet KV Cache growth limits long-context serving under constrained GPU memory. Offloading KV to CPU memory relieves this pressure. However, existing offloading schemes restore the full KV history before attention and fail to fully exploit the benefits of KV sharing across queries within a verification round. Existing parallel speculative decoding methods also overlook idle GPU compute capacity while memory-bandwidth-bound Target verification waits for historical KV. We present SpecStream, a speculative decoding system that begins verification without waiting for the full KV history to be restored and exploits compute bubbles during KV transfers for concurrent drafting on the same GPUs. It offloads only Target-committed history, keeping candidate rollback local to the GPUs. Each streamed KV chunk serves all queries in the round, with online softmax preserving full attention. Target-priority scheduling controls Draft concurrent execution under resource limits to constrain interference with Target verification. Experiments show that SpecStream maintains task quality close to SGLang speculative decoding while supporting more concurrent requests under limited GPU memory. Across different datasets, it achieves average throughput speedups of 1.41$\times$ and 1.32$\times$ over the offloading baseline for Qwen3 and InternLM2.5, respectively. Compared with parallel speculative decoding on separate Target and Draft GPUs, SpecStream improves output throughput per GPU by an average of 55.4%.

# 论文总结：Resource-Efficient Speculative Decoding for Long-Context LLM Serving

## 1. 核心问题与研究动机

- **背景**：长上下文 LLM 服务面临 KV Cache 随序列增长而膨胀的显存压力。推测解码（Speculative Decoding）通过草稿模型并行生成多个候选 token、由目标模型一次前向验证，减少顺序调用目标模型的次数，从而加速生成。
- **核心矛盾**：
  - 推测解码虽然缩短了顺序执行路径，但目标模型与草稿模型的权重、KV Cache、候选状态和缓冲区共同竞争显存，反而可能更早触及显存上限。
  - 将 KV 历史卸载到 CPU 内存可缓解显存压力，但**现有卸载方案必须先把完整 KV 历史恢复到 GPU 才开始注意力计算**，传输时间随上下文长度增长，成为目标验证的关键路径瓶颈。
- **被忽视的机会**：
  - 验证轮次内的 q 个查询虽因果可见性不同，但**共享同一段已提交历史 KV**，一次传输可服务整个查询组，实现传输成本摊薄。
  - 目标验证受内存带宽限制、等待历史 KV 时，GPU 计算单元处于空闲状态（compute bubble），可被草稿模型利用。
- **现有并行推测方案的不足**：MineDraft、SPECTRE、SwiftSpec 等通过跨 GPU 并行或流水线调度隐藏部分草稿延迟，但未直接利用这些计算气泡在同批 GPU 上推进草稿模型。

## 2. 方法论：SpecStream

### 2.1 整体思想
SpecStream 围绕推测解码中 KV Cache 的状态与访问特性，联合设计**历史管理、流式计算与共享 GPU 调度**三部分，使目标验证无需等待完整 KV 历史即可开始，并利用传输等待气泡在同一 GPU 上并行推进草稿。

### 2.2 提交感知的无回滚 KV 分层（Commit-Aware Rollback-Free KV Tiering）

- **状态划分**（公式 4）：
  - `Sealed History [0, H)`：已提交且迁移完成的历史，位于 CPU
  - `Active Tail [H, Cr)`：近期已提交 KV，位于 GPU
  - `Speculative Frontier [Cr, Lr)`：待验证候选 KV，位于 GPU
  - 约束：`0 ≤ H ≤ Cr ≤ Lr`
- **关键点**：迁移边界由目标模型的提交边界 `Cr` 决定，只卸载不可撤销的已提交前缀；候选的回滚仅发生在 GPU 上的推测后缀，回滚范围与 CPU 历史 KV 不相交，避免为可能被拒绝的候选做无用传输和 CPU 侧清理。
- **批量迁移**（公式 5）：保留长度为 `T` 的 Active Tail，按粒度 `g` 对齐后迁移 `[H, E)`，其中 `E = max(H, g·⌊max(0, Cr−T)/g⌋)`；迁移异步执行，确认完成后才推进 `H` 并回收 GPU 空间。

### 2.3 多查询验证的 KV 流式传输（KV Streaming for Multi-Query Verification）

- **分块共享**：将当前层 Sealed History 沿 token 位置切分为 J 个连续块，每块 `(Kj, Vj)` 到达 GPU 后，用整轮查询组 `Q ∈ R^{q×dh}` 计算 `Sj = QKj^T/√dh`，一次传输服务全部 q 个查询。
- **在线 softmax 保持完整因果注意力**：为每个查询和注意力头维护累加器 `(m, ℓ, a)`：
  - 初始 `(−∞, 0, 0)`；
  - 每块先算局部状态 `mj = max(Sj)`、`ℓj = Σ e^{Sj,k−mj}`、`aj = Σ e^{Sj,k−mj}Vj,k`；
  - 合并时取 `m′ = max(m, mj)`，缩放因子 `α = e^{m−m′}`、`β = e^{mj−m′}`，更新 `ℓ′ = αℓ + βℓj`、`a′ = αa + βaj`；
  - 全部可见 KV 处理完后输出 `O = a/ℓ`，等价于一次性计算完整 softmax（仅改变归约顺序）。
- **流水线与预取**：双 GPU staging buffer + 独立传输/计算流实现 H2D 与注意力计算重叠；相邻块合并为传输批次；当前层释放缓冲后预取下一层历史 KV。
- **Cohort 批处理**：将同一调度批次中兼容（同层、同验证宽度、同数据类型、同 KV 头数/头维度/块大小）的任务归组，用批量注意力内核执行，摊薄数据准备、同步与内核启动开销。
- **I/O 感知的动态验证宽度**：依据 `q* = arg min_{q∈Q} ( T̂round(q)/Û(q) )` 选择宽度，Q = {2,4,6,8}，结合传输成本、接受长度与执行开销，在切换收益超过阈值时才改变 q。

### 2.4 目标优先的 GPU 内协同执行（Target-Priority Intra-GPU Co-Execution）

- **资源分配**：使用 NVIDIA MPS 支持目标与草稿进程在同一 GPU 上并发；通过 TPC（Texture Processing Cluster）掩码限制草稿模型的算力范围，保留目标模型原有资源访问。
- **离线测量**：扫描不同 TPC 数量下的草稿单步时间 `tD(x,n)` 与目标验证延迟增幅 `ΔT(x,n) = [T^co_T(x,n) − T^alone_T(x)]/T^alone_T(x)`，选定默认分配 `n0`（实验为 34 TPC/GPU）。
- **运行时调度**：仅当 `Δ̂T(x,n0) ≤ εT` 且 `t̂D(x,n0) + δ ≤ Ŝ`（剩余窗口）时提交一步草稿；每次只允许**单 token 的完整草稿前向**，携带请求/轮次标识、序号、TPC 分配与最晚启动时间 `tlatest`，完成后返回 ACK 再决定是否继续；若干扰超预算则停止提交新步骤，恢复目标独占执行。

## 6. 主要结论与发现

- **质量保持**：SpecStream 与 SGLang SD 的最大质量差为 0.1988 个百分点，流式验证仅改变归约顺序，精度差异源于浮点累加顺序扰动。
- **吞吐提升**：
  - 相比 TriForce，Qwen3 与 InternLM2.5 平均加速 **1.41×** 和 **1.32×**；相比 SD+Offload 为 **1.44×** 和 **1.62×**。
  - GSM8K 短输入上比 SGLang SD 提升 16.9% 和 10.6%，动态宽度使平均接受长度分别增加约 16% 和 28%。
- **并发扩展**：在显存受限下支持更多并发请求；32 并发时 CPU KV 峰值达 45.50 和 49.50 GiB/GPU。
- **共享 GPU 调度**：相比串行执行提升 9.9%–43.6% 和 2.7%–31.7%；相比三 GPU 的 SPECTRE+Offload，平均吞吐为 1.036×，按 GPU 数归一化后每 GPU 吞吐平均提升 **55.4%**。
- **消融结论**：流式访问（K2）贡献最大（16K 输入下比 K1 提升 83.2%/117.1%）；预取（K3）再提升 4.5%–15.6%/3.0%–15.3%；动态宽度（K4）收益依模型与负载而异；Cohort（K5）在多请求下提升 4.6%–17.3%。
- **重要反直觉发现**：平均接受长度增加**不保证**吞吐提升（InternLM2.5 8 请求时接受长度 3.64→6.22，吞吐反降 1.2%）。

## 7. 优点

- **问题洞察精准**：识别出验证轮内 KV 共享与传输等待气泡这两个被忽视的机会，并将其转化为系统设计。
- **状态语义清晰**：以目标提交边界划分迁移与回滚区域，从机制上避免为被拒候选做无用传输，设计优雅且正确性强。
- **数学严谨性**：用在线 softmax 严格保持完整因果注意力，仅改变归约顺序，理论上与全量 softmax 等价。
- **协同设计**：KV 管理、流式计算、GPU 调度三者联动，而非孤立优化。
- **资源效率视角突出**：以“每 GPU 吞吐”作为关键指标，论证用 2 块 GPU 达到 3 块 GPU 方案的吞吐，具备实际部署价值。
- **消融设计规范**：累积式消融 + 相同 KV 预算与输入，因果归因清晰。

## 8. 不足与局限

- **长输入场景仍落后**：LongBench v2 和 MRCR 上吞吐仍低于全 GPU 驻留的 AR 和 SGLang SD，因为历史 KV 每轮都要走 PCIe（Gen4 ×16 约 31.5 GB/s，远低于 A800 HBM 的 1935 GB/s）。
- **草稿 KV 未卸载**：当前实现完整保留草稿模型 KV 于 GPU，随并发增长占用显存，成为进一步扩展 batch 的瓶颈；论文也指出草稿连续步之间缺乏多查询复用机会，直接套用卸载路径会反复拉取历史 KV。
- **传输成本敏感**：Qwen3 在 32 并发时吞吐略高于 AR 但低于 SGLang SD，且累计 H2D 流量高达 7.79 TiB/GPU，说明性能对数据量高度敏感。
- **基线适配偏差风险**：TriForce 原实现面向 Llama，本文将其改造到 Qwen3/InternLM2.5，对比结果可能受改造质量影响。
- **统计严谨性不足**：未报告多次运行的方差、置信区间或显著性检验；质量对比仅有单次分数。
- **场景覆盖有限**：仅在 2 个模型对、3 个数据集上验证，未涉及更大模型、MoE 架构或更极端的上下文长度（如 128K+）。
- **硬件依赖**：方法依赖 NVIDIA MPS 与 TPC 掩码等特定硬件特性，跨厂商 GPU 的可移植性未讨论。
- **未来方向**：作者提出将 KV 卸载扩展到 CPU 内存之外的更多存储层级。
