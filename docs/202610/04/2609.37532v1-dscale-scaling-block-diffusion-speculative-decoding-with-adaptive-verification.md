## 摘要
日益增长的大语言模型应用需要高效推理。在高并发下，块扩散投机解码受到验证填充、候选被拒绝，以及可变前缀与固定形状图之间不兼容的困扰。统一截断会牺牲可接受 token。我们提出 DScale，保留草稿模型架构、权重和完整草稿长度。一个独立的 112K 参数预测器既不需要置信度校准，也不需要硬件速度曲线准备。路径感知的分块减少填充。动态验证长度（DVL）分配将已评分的前缀打包进原生验证容量的一半。固定地址工作区在验证与接受过程中传播不断变化的边界，同时复用已捕获的计算图。在张量并行度为 1 的 A100-40GB 上，Qwen3-8B 和 Qwen3-4B 覆盖四个数据集和并发度 8-32，复用每个目标模型的冻结预测器。在这些配置下，相比 DFlash，几何平均吞吐量增益分别为 43.9% 和 48.8%；相比 DSpark 分别为 22.2% 和 37.7%；相比 Domino 分别为 24.4% 和 32.0%，同时请求延迟更低。累积消融实验表明，依次加入这三个机制可逐步提高几何平均吞吐量，而预算调整则提升已接受 token 保留率。GPU 性能分析显示，在 GSM8K 上，完整解码步时间相对 DFlash 降低 30.8-52.5%。

## Abstract
Growing large language model applications demand efficient inference. At high concurrency, block-diffusion speculative decoding suffers from verification padding, rejected candidates, and incompatibility between variable prefixes and fixed-shape graphs. Uniform truncation sacrifices acceptable tokens. We present DScale, preserving drafter architecture, weights, and full draft length. A separate 112K-parameter predictor requires neither confidence calibration nor hardware speed-curve preparation. Path-aware tiles reduce padding. Dynamic verify-length (DVL) allocation packs scored prefixes into half the native verification capacity. Fixed-address workspaces propagate changing boundaries through verification and acceptance while reusing captured graphs. On A100-40GB with tensor parallelism 1, Qwen3-8B and Qwen3-4B cover four datasets and concurrency 8-32, reusing each target's frozen predictor. Geometric-mean throughput gains across these configurations are respectively 43.9% and 48.8% over DFlash, 22.2% and 37.7% over DSpark, and 24.4% and 32.0% over Domino, with lower request latency. Cumulative ablations show that adding the three mechanisms successively increases geometric-mean throughput, while budget adjustment improves accepted-token retention. GPU profiling shows that complete decode-step time on GSM8K decreases by 30.8-52.5% relative to DFlash

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：大语言模型（LLM）在线服务需要低延迟、高吞吐。自回归解码每步只生成一个 token，顺序执行限制了生成速度。投机解码（speculative decoding）通过小模型草稿 + 大模型并行验证，在一次前向中接受多个 token 来加速。
- **具体对象**：论文聚焦于**块扩散投机解码**（block-diffusion speculative decoding）中的 DFlash 方案——轻量草稿器（约 1B 参数、5 层）以目标模型多层隐藏特征为条件，在一次并行前向中生成完整候选块（1 个已知锚点 + 15 个新候选，共 W=16 个验证槽），再由目标模型验证。
- **高并发下的三大挑战**：
  - **挑战 1：负载形状不匹配的分块（Workload-shaped tiles）**。预填充处理长查询序列，验证处理很短的候选块，但二者共享同一注意力 tile 布局。原生 128 行 tile 对每个验证请求仅 16 行有效，**87.5%（112 行）被掩码**，掩码并不压缩编译后的 tile 或中间数组。
  - **挑战 2：请求级接受长度差异（Request-varying acceptance）**。不同请求实际接受的草稿长度不同（实测平均进度 6.09，长尾可达 16），但接受前缀在验证前未知；固定宽度无法匹配请求间差异，统一截断（如统一用 8）会牺牲长前缀，统一验证全宽又无法节省。
  - **挑战 3：固定验证图接口下的动态前缀（Dynamic prefixes under fixed graph）**。请求边界随步变化（如 `[4,12,8]`→`[10,8,6]`），若补齐回等宽接口就恢复了浪费；CPU 重切片会把主机依赖放到 GPU 关键路径上；DSpark 的桶式调度只能提供“桶粒度”的容量缩减。
- **整体含义**：论文目标是**在不改动草稿器架构、权重与完整草稿长度的前提下**，在高并发场景中减少验证侧浪费、保留有效接受 token，同时复用已捕获的 CUDA Graph，避免每步 CPU 同步。
- **关键动机证据**：Nsight 剖析显示，在 Qwen3-8B、GSM8K、A100、TP1、并发 16 下，目标验证图占 GPU kernel 总时间的 **83.3%**，草稿图占 10.9%，其余 5.7%——验证是主导瓶颈。此外，草稿侧 Top1–Top2 logit gap 与接受长度正相关（8B：Spearman ρ=0.741；4B：ρ=0.722），说明验证前即可预测接受潜力。

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 总体思想
- 保留 DFlash 草稿器（架构、权重、完整草稿长度），仅在**验证侧**做运行时优化；训练一个**独立的 112K 参数预测器**（每个目标–草稿对训练一次），**无需置信度校准（STS）与硬件速度曲线（SPS）准备**。
- 三大机制：**路径感知 tile 路由** + **动态验证长度（DVL）预算分配** + **固定地址工作区图集成**。

### 2.2 路径感知 Tile 路由（对应挑战 1）
- 按路径选择 tile 高度：验证路径最大查询长度 ℓmax ≤ W = 16，选择 **B = 16**；预填充与更长查询保留硬件选择的 **Bhw = 128** 以复用 KV。
- 运行时选择匹配 warp 与网格 `grid = (Nrun, H, ⌈ℓmax/B⌉)`；每个计算块处理一个请求的一个 head 的查询 tile。
- 查询行容量与填充比例公式：
  - `rows(ℓ,B) = B·⌈ℓ/B⌉`
  - `padding(ℓ,B) = 1 − ℓ / rows(ℓ,B)`
- ℓ=16、B=16 恰好容纳整块；更大 tile 增加无效行，更小 tile 无法进一步减少填充反而拆分 KV 复用。
- 该机制只消除超出最大验证宽度的填充；GEMM 与 LM-head 的行压缩由 DVL 单独处理。

### 2.3 DVL 预算分配（对应挑战 2）
- **容量设定**：活跃请求数 N、请求桶容量 Nbs、块宽 W=16（含锚点），
  - 捕获容量 `Mbs = W·Nbs/2 = 8·Nbs`
  - 活跃预算 `Mlive = W·N/2 = 8·N`，且 `Σ ki = Mlive`，`ki ∈ {1,…,W}`
- **接受预测器（Acceptance predictor）**：每请求特征维度 **1735**：
  - 每位置 18 个偏好/不确定性值（Top1 logit、与 rank2–16 的 15 个 gap、Top token log-prob、分布熵）→ 15×18 = **270**
  - 隐藏态投影 15×64 = **960**；logit 向量投影 15×32 = **480**
  - 批上下文 batchContext **25**（首项为活跃数 N，第 4 项为初始状态标志）
  - 结构：`1735–64–15` MLP + ReLU，输出每个新草稿位置的 predLogits
  - 用 Sigmoid 得接受分，**累积最小值**保证前缀分数非增：`q0=1, qj = min(q_{j−1}, σ(predLogits_j))`
  - 分数求和得到估计接受数 `ℓ̂i`，四舍五入并裁剪到 `[1,W]` 作为启发式初始长度 `k(0)_i`（含锚点）
  - 训练目标：平均二元交叉熵 + 0.02 ×（sigmoid 原始和与接受草稿数的 MSE），单调性约束前计算
- **预算分配器（Budget allocator）**：优化目标为
  - `max Σ_i Σ_{j=0}^{ki−1} q_{i,j}`，约束 `Σ ki = Mlive`，`1 ≤ ki ≤ W`
  - 从 `k(0)_i` 出发，计算差额 Δ；Δ>0 时给“下一槽增益最大”的请求加槽，Δ<0 时给“尾槽损失最小”的请求减槽，直到 Δ=0
  - 该循环在决策图内的**单个 GPU 计算块**中执行，无主机往返、无块间同步
  - **命题 1**：整数种子与预算下，算法在 |Δ0| 次更新内保持前缀与锚点并满足预算；在附加约束（Δ0>0 时 ki ≥ k(0)_i，Δ0<0 时 ki ≤ k(0)_i）下最大化目标函数
- **平坦缓冲打包器（Flat-buffer packer）**：用前缀和偏移 `offset_i = Σ_{j<i} kj`，对 tokens、positions、KV refs 三个字段做同一行映射 `buffer.field[offset_i + j] = field_i[j]`；注意力块按 ki 掩码；接受阶段复用偏移。
- **复杂度**：`Work_DVL = O(Nbs·d·h + N·Nbs·W² + Mbs·Nbs)`；W=16 时调整次数 ≤ 7N；实测分配器（预测器 + 预算分配 + 打包）在 c=8 时仅占 DScale 完整解码步 GPU 时间的 **3.08%（8B）/ 4.08%（4B）**。

### 2.4 图集成：参差决策的固定地址工作区（对应挑战 3）
- 固定地址工作区：各张量数组的**地址与形状跨步保持不变**（式 13）。
- 请求桶选择：`Nbs = min{ b ∈ B | b ≥ N }`；非活跃长度置零，尾部槽位不参与接受。
- 容量仍为 DFlash 同请求桶的一半：`Mlive + 8(Nbs − N) = 8Nbs = 16Nbs/2`。
- **算法 2（固定地址图捕获与回放）**：
  - 捕获阶段：对每个桶 Nbs 分配 buffer，捕获两条流水线 `Gdec_bs = [Features → DVL]` 与 `Gverify_bs = [Target → Accept → Output]`
  - 回放阶段：输入暂存 → 回放 Gdec → 等待 GPU（保证决策与先前 KV 写入的顺序）→ 由 offset 与 k 设置 qStart/qEnd → 收集 ctxLen 个已提交上下文 KV 到 historyKV → 回放 Gverify → 读输出 → 状态提交（追加 token、更新长度、更新下一锚点、移除完成请求）
  - 注意力掩码：`valid_i(j) = 1{1≤i≤N ∧ 0≤j<ki}`
- **前缀验证器（Prefix verifier）**：确定性 top-1 草稿以概率 P(x) 接受；首次拒绝时从去除 x 并重新归一化的 P 中采样后继；全部通过则用未修改的目标分布；第 offset_i + a_i 行给出后继 token，作为下一步锚点。DVL 长度选择与接受随机数独立，补充材料给出输出分布推导。
