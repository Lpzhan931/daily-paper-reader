## 摘要
推测解码通过使用轻量级草稿模型推测多个词元，减少昂贵的目标模型解码步骤，从而加速自回归大语言模型（LLM）推理。其有效性在很大程度上取决于草稿选择，这推动了利用输入和生成阶段差异的自适应方法。然而，在内存受限的边缘设备上，由于在草稿模型之间切换的开销，这些方法往往无法提高端到端吞吐量。我们发现了该设置中的一个关键限制：在严格内存预算下，草稿选择与草稿可用性之间的不匹配。为了解决这一挑战，我们提出了MemSpec，一种用于边缘设备上自适应推测解码的预测引导、内存感知运行时。MemSpec通过主动的驻留工作集管理将草稿选择与执行解耦。一个轻量级预测器根据提示和生成上下文估计草稿有效性，而一个内存感知调度器减少了反应式模型加载开销。在Jetson Orin Nano上的实验表明，与最先进的基于老虎机的自适应方法相比，MemSpec平均将稳态生成吞吐量提高了40.7%，同时接近oracle上限。

## Abstract
Speculative decoding accelerates autoregressive large language model (LLM) inference by using a lightweight draft model to speculate multiple tokens, reducing expensive target model decoding steps. Its effectiveness depends heavily on draft selection, motivating adaptive methods that exploit variation across inputs and generation stages. On memory-constrained edge devices, however, these methods often fail to improve end-to-end throughput due to the overhead of switching between draft models. We identify a key limitation in this setting: the mismatch between draft selection and draft availability under tight memory budgets. To address this challenge, we present MemSpec, a prediction-guided, memory-aware runtime for adaptive speculative decoding on edge devices. MemSpec decouples draft selection from execution through proactive resident working-set management. A lightweight predictor estimates draft effectiveness from prompt and generation context, while a memory-aware scheduler reduces reactive model loading overhead. Experiments on a Jetson Orin Nano show that MemSpec improves steady-state generation throughput by 40.7% on average over state-of-the-art bandit-based adaptive methods while closely approaching the oracle upper bound.

## 2. 提出的方法论：MemSpec

### 2.1 核心思想

- 将**草案选择与执行解耦**：预测决定"应该准备哪些草稿"，执行则限于"当前驻留的草稿"。
- 两大设计原则：
  1. **非阻塞执行**：始终从驻留集中选择最佳草稿执行，绝不因等待非驻留草稿而停顿。
  2. **主动驻留集管理**：根据预测的未来需求，预先调整驻留工作集（预取/驱逐），使草稿可用性与需求对齐。

### 2.2 系统架构与关键组件

MemSpec 包含三个核心组件（对应架构图）：

1. **预测引擎（Prediction Engine）**
   - 使用离线微调的 BERT 编码器（只训练排序头，encoder 冻结）作为预测器：`p_i = f_θ(x_i)`，对每个草稿输出一个得分。
   - 输入 `x_i` 为当前上下文，由 `x_i = [x_prompt; x_recent(T)]` 构成——即**提示 + 最近 T 个生成词元**。提示捕获全局任务语义，最近词元捕获生成阶段变化（如从推理过渡到代码生成）。
   - 每隔 N 次推测解码迭代调用一次，排序得到候选草稿列表 `R_i = Sort(p_i)`，其开销平均仅占总体执行时间的 3.9%。

2. **草稿模型缓存管理器（Draft Model Cache Manager）**
   - 维护驻留集 `G_i`，在容量 K（最多 K 个草稿模型常驻）下工作。
   - 调度点处，从排名列表取 Top-K 作为目标工作集 `W_i`。
   - 渐进式更新驻留集：对 `W_i \ G_i` 中的草稿发起**异步预取**；按预测效用升序驱逐非目标草稿，并**优先保护当前活跃草稿**不被驱逐。

3. **运行时控制器（Runtime Controller）**
   - 核心策略：**始终执行当前驻留集中得分最高的草稿**，绝不因非驻留模型而停顿。
   - 初始时根据 prompt 预测并加载首个草稿；每个调度间隔内运行 N 次推测解码迭代；随后用最新生成词元构造下一上下文，触发预测与缓存更新，再从驻留集中选出下一激活草稿。
   - 这样将草稿切换转化为"分阶段、可重叠"的过程，而非"停顿密集的即时切换"。

### 2.3 关键公式与算法流程

- 吞吐公式：`Throughput ≈ E[A] / L_iter`（A 为一次迭代接受词元数，L_iter 为一次 SD 迭代延迟）。
- 初始草稿选择：`d_0 = argmax_d P(d | x_prompt)`。
- 排名：`p_i = {P(d | x_i) | d ∈ D}`；候选列表 `R_i = Sort(p_i)`；目标工作集 `W_i = TopK(R_i)`。
- 激活草稿：`d*_i = argmax_{d ∈ G_i} P(d | x_i)`——注意从驻留集而非全集中选择。
- 算法流程：
  - **Algorithm 1（上下文感知草稿排序）**：输入 prompt、最近词元、候选集；构建上下文 `[prompt; recent]` 或仅 prompt（i=0）→ 计算所有草稿得分 → 排序输出 R_i。
  - **Algorithm 2（草稿缓存更新）**：从 R_i 取 Top-K 得到 W_i → 对每个在 W_i 但不在驻留集且未预取中的草稿，若容量满则选择驻留集中 "不在 W_i 且非活跃草稿" 中得分最低者驱逐 → 异步预取新草稿。
  - **Algorithm 3（运行时主循环）**：加载目标模型 → 初始预测排名 → 加载初始草稿 → 初始化驻留集 → 循环执行 N 次 SD 迭代 → 构造下一上下文 → 预测排名 → 更新缓存 → 从驻留集中选择下一活跃草稿。

## 3. 实验设计

### 3.1 硬件平台

- 主实验平台：**NVIDIA Jetson Orin Nano**（Ampere GPU，1024 CUDA 核心，32 Tensor 核心，6 核 Arm Cortex-A78AE CPU，8GB LPDDR5，1TB NVMe SSD）。
- 缓存容量敏感性实验额外使用 **Jetson AGX Orin**（更大内存平台）。

### 3.2 模型与数据集

- **目标模型**：GPTQ INT4 量化的 LLaMA-2 7B 和 Qwen2.5 7B。
- **草稿模型**：每个目标模型族对应 5 个 400M 参数（LLaMA-2）/0.5B 参数（Qwen2.5）草稿——1 个通用草稿 + 4 个领域专用草稿（数学、代码、法律、医疗），通过蒸馏/微调获得。在 8GB 内存约束下，最多同时驻留 2 个草稿模型（K=2）。
- **评估工作负载**（5 个数据集，各随机采样 100 条 prompt）：
  - Alpaca（指令跟随）
  - LiveCodeBench（代码）
  - Omni-MATH（数学）
  - MMLU-Law（法律）
  - MMLU-Medical（医疗）
- **预测器训练**：使用与草稿微调相同的数据集运行推测解码并记录执行 trace，训练 BERT 排序头选择"解码效用最高"的草稿；训练数据与评估数据集不重叠。

### 3.3 运行时配置

- 默认调度间隔 N=4，输出长度 128 tokens，贪心解码，batch size 1。
- 吞吐量为稳态迭代解码吞吐（排除 prompt 编码时间），每次运行 3 次取平均，报告几何均值（GMEAN）。

### 3.4 对比方法（Baselines）

1. **General-Static**：固定使用通用（非微调）草稿。
2. **Oracle-Static**：离线评估选择每 prompt 最优草稿，生成过程中固定。
3. **MAB-Async**：UCB 策略的异步 bandit 自适应方法（类似 BanditSpec），草案加载与解码重叠，初始先探索每个草稿一次，探索系数经调参取 c=2.0 最优配置。
4. **Oracle-Dynamic**：实证上界，在同样调度间隔下用 oracle 知识选择每调度点最优草稿，同样受内存约束。
5. **MemSpec**：本文方法。

### 3.5 实验组别

- 整体吞吐对比（两种目标模型 × 5 个数据集）
- 执行时间分解（期望执行 vs. 兜底执行 vs. 预测开销）
- 组件消融分析（General-Static vs. Prediction-Only vs. 完整 MemSpec）
- 敏感性分析（调度间隔 N ∈ {2,4,8,16}；输出长度 ∈ {64,128,256}；驻留容量 K ∈ {2,3,4}）
- 预测器质量对比（prompt-only / recent-only / prompt+recent 三种输入配置）
- 端到端延迟对比（含预填充与初始加载，验证启动开销影响）

## 6. 主要结论与发现

1. **静态选择不够**：Oracle-Static 相对 General-Static 平均提升 token 接受率 40.3%、吞吐 22.5%；而 Oracle-Dynamic 相对 Oracle-Static 再提升 25.7%（接受率）/24.9%（吞吐），说明最优草稿在单个生成序列内部会随阶段变化，动态适应存在显著额外空间。
2. **切换开销是关键瓶颈**：加载非驻留草稿耗时是单次 SD 迭代的 2.7 倍；MAB-Sync 执行时间被模型加载主导，MAB-Async 也花费 46.4%–49.4% 的时间在"兜底执行"上——即等待偏好草稿加载期间用次优草稿解码。
3. **MemSpec 效果显著**：
   - 稳态生成吞吐相对 General-Static 平均提升 58.8%，相对 MAB-Async 平均提升 40.7%，达到 Oracle-Dynamic 上界的 95%–97%。
   - 将兜底执行从 MAB-Async 的 ~49% 降至 5.5% 以下，预测开销仅占 3.9%。
4. **组件贡献**：Prediction-Only（预测但不主动预取）相对 General-Static 提升 21.6%，但完整 MemSpec 再提升 30.5%，证明**预测必须与驻留管理耦合**才能兑现收益。
5. **预测器质量**：prompt+recent 结合输入达到 Top-1 准确率 71.6%、Top-2 召回 95.7%——最优草稿几乎总能进入驻留工作集，说明"足够好的排名"比"完美预测"更关键。
6. **对参数不敏感**：调度间隔 N=4~8 时性能平稳，表明无需精细调参；提升幅度随输出长度增长而增大（长文本受益更大）；在更大缓存容量（K=3/4）下 MemSpec 仍优于 MAB-Async。

"执行驻留集（现在能执行什么）"的分离，配合异步预取与活跃草稿保护，将高开销的即时切换转化为低开销的分阶段更新，设计简洁且工程可实现性好。
- **实验设计严谨**：包含 oracle 上界/下界对照、bandit 基线的超参数调优、组件消融、多维度敏感性分析以及跨平台验证，证据层次丰富；训练/评估数据隔离，且预测器开销被显式测量（3.9%），增强了结论可信度。
- **写作与论证清晰**：每个设计决策都有动机与数据支撑（如 2.7 倍加载开销、46.4%–49.4% 兜底占比），"问题—洞察—方法—验证"的叙事结构完整，读者容易复现主要思想。

## 8. 缺点与局限性

- **草稿池规模过小且同质性较强**：每个目标模型仅配 5 个同参数量级（400M/0.5B）的草稿，且领域草稿从同一基础模型蒸馏而来。实际场景中草稿模型可能数量更多（10+）、结构差异更大（不同量化位宽、不同架构），MemSpec 在更大、更多样化草稿池下的预取调度与预测器排序质量均未验证。
- **预测器训练依赖领域先验与数据源**：预测器是在与草稿微调相同领域的数据上训练的，且训练数据需通过"已部署推测解码系统"采集执行 trace 获得，存在鸡生蛋问题（新领域冷启动时需要先有执行数据）。对 open-domain、分布漂移环境的鲁棒性缺乏讨论。
- **分析粒度偏粗**：吞吐统计排除了 prompt 编码时间与模型持久化存储往返，且仅报告稳态平均；缺乏对尾部延迟（tail latency）、加载失败重试、预取争用 NVMe 带宽等异常情形的分析。
- **对比基线覆盖面有限**：未与近年更先进的自适应草稿方法（如 Not-a-Bandit、动态草稿长度调整、多草稿并行验证等）对比；也未与"多草稿同时驻留并通过投票/融合增强验证"类方法对照。
- **评估规模偏小**：每数据集仅 100 条 prompt、生成 128 tokens（敏感性实验最长 256），统计功效有限；且未报告逐条方差或置信区间，GMEAN 虽稳健但掩盖了极端情况下的性能退化可能。
- **硬件场景单一**：仅涉及 Jetson 系列嵌入式平台，未在数据中心 GPU（如 A100/H100）或 CPU-only 边缘设备上验证；"加载成本 2.7×迭代延迟"这一关键数值依赖具体 I/O 结构，结论向其他硬件迁移的泛化性存疑。

## 9. 个人思考与启示

- **问题重定义的示范价值**：本文最重要的贡献不是提出了一个新的选择算法，而是把"选择最优草稿"重新定义为"内存约束下的调度问题"。这种"将资源约束前置到算法设计"的思路，对边缘 AI 系统中所有"模型选择/级联/路由"类问题（如多模型服务、专家混合路由）都有迁移价值。
- **预测优于探索的启示**：在切换成本高的系统中，bandit 式在线探索的代价被放大到不可接受——每一步探索都可能付出一次昂贵的模型加载。这提示在"动作切换成本 >> 动作执行成本"的边缘场景中，离线先验 + 预测引导往往比在线学习更实用，而"预测近优 + 执行无损"的组合（预测 Top-K 进入驻留集，激活时取驻留集中最优）优于追求瞬时最优选择。
- **"减少浪费"的工程智慧**：主动预取 + 保护活跃草稿 + 非阻塞执行的本质是把确定性开销（加载）隐藏在非关键路径上，并容忍"预测次优"而非"预测错误"——只要 Top-2 召回率足够高（95.7%），最佳草稿几乎总在驻留集内。这种"以概率保证代替精确匹配"的系统思维值得借鉴。
- **可扩展方向**：(1) 将预测器从 BERT 换为更轻量的 n-gram/统计特征或在线自适应的轻量模型，降低冷启动成本；(2) 将驻留容量 K 与草稿模型的内存占用、加载带宽建模为显式优化问题；(3) 扩展到多目标模型共享草稿池的服务端场景；(4) 与草稿长度动态规划（如动态最大推测长度）联合优化，进一步提升上界。
- **对读者/实践者的建议**：若要在自己的边缘部署中复现收益，需先测量"草稿加载/卸载耗时 vs. 单次 SD 迭代耗时"之比——只有当该比值足够大（例如 >1）时，MemSpec 式的显式驻留管理才比简单 LRU 缓存或固定草稿更有优势；若比值接近 1，则朴素异步切换即可，不必引入预测器。

## 10. 一句话总结

MemSpec 将边缘设备上的自适应推测解码从"草稿选择问题"重构为"驻留约束下的调度问题"，通过轻量预测器引导目标工作集 + 异步预取 + 非阻塞激活草稿选择，在不增加推理延迟的前提下将端到端吞吐较最强 bandit 基线提升 40.7%，并达到 oracle 动态上界的 97%，为内存受限设备上的高效 LLM 推理提供了"用轻量预测替代昂贵探索"的系统性方案。
