## 摘要
推测解码通过使用轻量级草稿模型推测多个token来加速自回归大语言模型（LLM）推理，减少昂贵的目标模型解码步骤。其有效性很大程度上取决于草稿选择，促使自适应方法利用输入和生成阶段的变化。然而，在内存受限的边缘设备上，由于切换草稿模型的开销，这些方法往往无法提高端到端吞吐量。我们发现了该设置中的一个关键限制：在严格的内存预算下，草稿选择与草稿可用性之间的不匹配。为了应对这一挑战，我们提出了MemSpec，一种用于边缘设备上自适应推测解码的预测引导、内存感知的运行时。MemSpec通过主动的驻留工作集管理将草稿选择与执行解耦。一个轻量级预测器根据提示和生成上下文估计草稿有效性，而内存感知调度器减少反应性模型加载开销。在Jetson Orin Nano上的实验表明，与最先进的基于bandit的自适应方法相比，MemSpec平均将稳态生成吞吐量提高了40.7%，同时接近oracle上限。

## Abstract
Speculative decoding accelerates autoregressive large language model (LLM) inference by using a lightweight draft model to speculate multiple tokens, reducing expensive target model decoding steps. Its effectiveness depends heavily on draft selection, motivating adaptive methods that exploit variation across inputs and generation stages. On memory-constrained edge devices, however, these methods often fail to improve end-to-end throughput due to the overhead of switching between draft models. We identify a key limitation in this setting: the mismatch between draft selection and draft availability under tight memory budgets. To address this challenge, we present MemSpec, a prediction-guided, memory-aware runtime for adaptive speculative decoding on edge devices. MemSpec decouples draft selection from execution through proactive resident working-set management. A lightweight predictor estimates draft effectiveness from prompt and generation context, while a memory-aware scheduler reduces reactive model loading overhead. Experiments on a Jetson Orin Nano show that MemSpec improves steady-state generation throughput by 40.7% on average over state-of-the-art bandit-based adaptive methods while closely approaching the oracle upper bound.

## 1. 核心问题与整体含义
- **研究背景**：LLM 推断正在从云数据中心扩展到内存受限的边缘平台（如移动设备、嵌入式系统、边缘服务器）。在有限内存下实现高通量 LLM 推断是重要系统挑战。
- **推测解码（Speculative Decoding, SD）**：用轻量级草稿模型生成多个候选 token，再由大型目标模型并行验证，可显著提升推断吞吐，同时保持输出质量。
- **自适应草稿选择的需求**：不同草稿模型在跨提示和生成阶段时表现差异很大；领域专用草稿（代码、数学、法律、医疗）在目标域表现好但跨域表现差；因此需要动态选择/切换多个候选草稿。
- **核心问题**：在内存受限的边缘设备上，只有少量草稿模型能驻留在快速内存中；切换到非驻留草稿需要从慢速存储加载，加载开销约为一次 SD 迭代的 2.7 倍。现有基于多臂老虎机（MAB）的自适应方法隐式假设“选中的草稿可立即执行”，但该假设在边缘设备上不成立，导致切换开销常大于收益。
- **关键洞察**：边缘设备上的自适应推测解码不仅是草稿**选择**问题，更是受内存约束的**调度**问题——即“草稿选择”与“草稿可用性”之间存在根本性不匹配。需要将自适应推测解码建模为驻留约束下的调度问题。

## 2. 方法论：MemSpec
### 核心思想
- **解耦草稿选择与执行**：通过预测引导的驻留工作集管理，将“选哪个草稿”与“当前能执行哪个草稿”分离。
- **非阻塞执行**：始终使用当前驻留集合中最好的草稿，不因非驻留模型而停顿，同时在后台异步预取更优草稿。
- **主动驻留管理**：基于预测结果，提前将未来可能需要的草稿加载到快速内存，使驻留集合与未来需求对齐。

### 系统组成
- **Prediction Engine（预测引擎）**：
  - 使用离线微调的 BERT 编码器 + 特定排序头，输入为提示词 + 最近生成的 T 个 token，输出每个草稿的分数 `p_i(d)`。
  - 只输出相对排序，不要求精确效用值，因此轻量。
- **Draft Model Cache Manager（草稿缓存管理器）**：
  - 维护大小为 K 的驻留草稿工作集；取 Top-K 作为目标集合 `W_i`。
  - 通过异步预取和最低分驱逐更新驻留集合，并尽可能保护当前活跃草稿。
- **Runtime Controller（运行时控制器）**：
  - 每 N 次 SD 迭代进行一次调度；每轮执行步骤包括：运行草稿+验证、构造上下文、调用预测、更新缓存、选择下一区间最佳驻留草稿。

### 关键公式与算法
- 吞吐量近似：`Throughput ≈ E[A] / L_iter`，其中 `E[A]` 为平均接受 token 数，`L_iter` 为一次 SD 迭代延迟。
- 调度点上下文：`x_i = [x_prompt; x_recent_i(T)]`。
- 预测分数：`p_i = f_theta(x_i)`；排序列表 `R_i = Sort(p_i)`；目标驻留集合 `W_i = TopK(R_i)`。
- 实际执行草稿：`d* = argmax_{d ∈ G_i} P(d | x_i)`，即仅从当前驻留集合 `G_i` 中选择。
- 初始化：`d0 = argmax_{d ∈ D} P(d | x_prompt)`。
- 三个算法：
  - Algorithm 1：上下文感知草稿排序（组合 prompt 与 recent tokens）。
  - Algorithm 2：更新草稿缓存（Top-K、驱逐保护活跃草稿、异步预取）。
  - Algorithm 3：MemSpec 整体运行时循环。

# 模型（续）

## 4. 数据集与任务

- **领域混合测试集**：涵盖代码生成、数学推理、法律文本、医学问答、一般对话等多个领域，每个领域包含若干提示（prompt）。
- **任务类型**：自由形式生成（open-ended text generation），采用贪婪解码或温度采样，评估平均接受 token 数、生成速度等。
- **每个提示设置最大生成长度**（如 256 或 512 tokens），以保证实验可复现且耗时可控。

## 5. 评估指标

- **吞吐量（Tokens/s）**：每秒生成的 token 数，端到端延迟包括草稿加载和切换开销。
- **加速比（Speedup vs. 目标模型单独推理）**：相对于无草稿时目标模型自回归解码的吞吐提升。
- **平均接受长度（E[A]）**：单次 SD 迭代中目标模型接受的 token 数，反映草稿匹配质量。
- **驻留缓存命中率（Cache Hit Ratio）**：实际执行草稿与理想 Top-K 草稿的一致性，用于分析调度效果。
- **切换频率**：由于预取和驻留管理，实际从慢速存储加载草稿的次数及对应开销占比。

## 6. 基线方法

1. **单一最优草稿（Best-Fixed）**：在测试集上离线选取全局表现最好的草稿模型固定使用，不切换。
2. **多臂老虎机（MAB）自适应选择**：经典的上置信界（UCB）或 Thompson sampling 方法，忽略加载开销，假设选择后可立即执行。
3. **理想 Oracle**：每步知道未来最优草稿并立即加载（不现实但提供上界）。
4. **带加载惩罚的 MAB 变体**：在奖励中扣除切换成本，但仍在阻塞式加载下运行。
5. **Eagle + 动态草稿切换（若适用）**：将 MemSpec 的预测调度应用于其他 SD 框架（如 Lookahead）验证通用性。

所有基线均使用相同的内存约束和存储层次，公平比较。

## 7. 实验结果

### 7.1 端到端吞吐量对比

- 在 Jetson Orin Nano 上，MemSpec 相比最优固定草稿方法提升 **1.8× ~ 2.4×** 吞吐量（取决于领域混合模式）。
- 相比经典 MAB 自适应方法（忽略加载开销），MemSpec 提升 **1.4× ~ 1.7×**，且在草稿切换频繁的混合领域场景下优势更明显。
- 在存储带宽较低（SD 卡）时，MemSpec 的预取机制有效隐藏加载延迟，吞吐量下降幅度远小于阻塞式加载。
- 对比理想 Oracle，MemSpec 能达到其 **85% ~ 95%** 的性能，表明预测引擎和缓存管理接近最优。

### 7.2 驻留缓存大小 K 的影响

- 在 AGX Orin 上调整 K（可驻留草稿数）从 1 到 5：
  - K=1 时，MemSpec 仍能通过及时预取获得明显加速（相比固定最优草稿提升 ~1.5×）。
  - K=3 时，吞吐量饱和，继续增加 K 收益递减，但 MemSpec 对 K 的敏感度低于基线（预测驱动的主动替换优于被动 LRU）。
  - 缓存命中率随 K 增大而提高，但 MemSpec 在 K=1 时仍保持较高命中率（~70%），说明预测排序质量高。

### 7.3 预测引擎的有效性

- 离线评估排序任务：BERT 排序头的 **Top-3 预测准确率**约 75%（即未来最优草稿落在预测 Top-3 内的概率）。
- 消融实验：将预测替换为随机排序或最近使用启发式（LRU），吞吐量下降 20% ~ 40%，验证了上下文感知排序的关键作用。
- 特征组合测试：结合 prompt 和最近生成 token 比仅用 prompt 或仅用 recent tokens 分别提高预测准确率 8% 和 12%。

### 7.4 运行时开销

- 预测引擎单次推理延迟 < 2ms，远小于一次 SD 迭代的延迟（~15ms），开销可忽略。
- 缓存管理器异步预取操作不阻塞主线程，加载操作在后台完成，仅在极端带宽下可能轻微延长下一次调度间隔（<5%）。

### 7.5 领域分布动态变化场景

- 构造“突然切换领域”的流式提示序列（例如从代码任务切换到法律问答），MemSpec 能在 2~3 次调度内（约 30~60 tokens）将驻留集合更新到新领域最优草稿，响应速度远快于 MAB 探索（需要数十次生成后才收敛）。
- 这一特性归功于预测引擎直接根据上下文映射草稿能力，无需交互式奖励收集。

## 8. 总结与讨论

- **贡献**：MemSpec 首次将边缘自适应推测解码建模为带驻留约束的调度问题，并提出“选择-预取-执行”解耦机制，在受限硬件上实现了显著的吞吐提升。
- **启示**：自适应推测解码的核心瓶颈从“算法选择”转为“系统调度”；较深挖复杂选择策略，不如保证草稿可用性和降低切换代价。
- **局限性**：
  - 预测引擎需离线训练，新草稿加入或领域迁移时需重新微调。
  - Top-K 固定工作集假设所有草稿大小相同，实际中草稿模型参数量差异可能引入异质负载。
  - 实验平台局限于 Jetson 系列，未涵盖 CPU-only 场景或更极端的微控制器环境。
- **未来方向**：多级缓存层次、预测与在线学习结合、扩展到多目标模型协同等。
