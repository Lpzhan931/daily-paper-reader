## 摘要
推测解码通过使用轻量级草稿模型推测多个词元，减少昂贵的目标模型解码步骤，从而加速自回归大型语言模型（LLM）推理。其有效性很大程度上取决于草稿选择，这促使了利用输入和生成阶段差异的自适应方法。然而，在内存受限的边缘设备上，这些方法往往因草稿模型切换的开销而无法提升端到端吞吐量。我们发现了该场景中的一个关键限制：在紧张的内存预算下，草稿选择与草稿可用性之间存在不匹配。为应对这一挑战，我们提出了MemSpec，一种用于边缘设备自适应推测解码的预测引导、内存感知运行时。MemSpec通过主动的常驻工作集管理将草稿选择与执行解耦。一个轻量级预测器根据提示和生成上下文估计草稿有效性，而内存感知调度器则减少反应式模型加载开销。在Jetson Orin Nano上的实验表明，与最先进的基于bandit的自适应方法相比，MemSpec将稳态生成吞吐量平均提高了40.7%，同时接近oracle上界。

## Abstract
Speculative decoding accelerates autoregressive large language model (LLM) inference by using a lightweight draft model to speculate multiple tokens, reducing expensive target model decoding steps. Its effectiveness depends heavily on draft selection, motivating adaptive methods that exploit variation across inputs and generation stages. On memory-constrained edge devices, however, these methods often fail to improve end-to-end throughput due to the overhead of switching between draft models. We identify a key limitation in this setting: the mismatch between draft selection and draft availability under tight memory budgets. To address this challenge, we present MemSpec, a prediction-guided, memory-aware runtime for adaptive speculative decoding on edge devices. MemSpec decouples draft selection from execution through proactive resident working-set management. A lightweight predictor estimates draft effectiveness from prompt and generation context, while a memory-aware scheduler reduces reactive model loading overhead. Experiments on a Jetson Orin Nano show that MemSpec improves steady-state generation throughput by 40.7% on average over state-of-the-art bandit-based adaptive methods while closely approaching the oracle upper bound.

## 1. 论文的核心问题与整体含义

**研究动机与背景：**

- 大语言模型（LLM）正从云端向资源受限的边缘设备（如移动设备、嵌入式系统）迁移，在紧张的内存预算下实现高吞吐量推理成为关键系统挑战。
- 推测解码（Speculative Decoding）通过轻量级草稿模型生成候选词元，再由目标模型验证，可显著加速自回归解码。
- 不同草稿模型（如代码、数学、法律、医学等领域专用草稿）在不同提示和生成阶段的有效性差异很大，因此自适应草稿选择方法被提出。
- 然而，在内存受限的边缘设备上，切换非驻留草稿模型需要从慢速存储（如NVMe SSD）加载，加载延迟可达单次解码迭代的2.7倍（约超过3倍）。现有的基于多臂老虎机（MAB）的自适应方法虽然能提升草稿选择质量（token acceptance），却因频繁模型加载和fallback执行而无法转化为端到端吞吐量提升。

**核心问题识别：**

- 作者指出了现有方法的关键缺陷：**草稿选择与草稿可用性之间的不匹配（mismatch between draft selection and draft availability）**。
- 一个被预测为有效的草稿，在内存约束下可能无法立即执行，导致自适应方法在边缘设备上失效。
- 因此，边缘设备上的自适应推测解码不仅是一个**选择问题**，更是一个**内存约束下的调度问题**。

## 2. 论文提出的方法论

**核心思想：**

MemSpec 将自适应推测解码重新定义为**驻留约束下的调度问题（residency-constrained scheduling problem）**，通过预测引导和内存感知管理实现草稿选择与执行解耦，从而在不阻塞解码的前提下逐步将驻留工作集推向更优的草稿集合。

**三个关键组件：**

1. **预测引擎（Prediction Engine）**：
   - 使用离线微调的 BERT encoder 作为预测器，输入为提示（prompt）和最近生成的 T 个词元，输出各草稿的匹配分数向量 p_i = [p_i(d_1), ..., p_i(d_|D|)]。
   - 替代在线探索（如MAB），避免昂贵的在线探测开销。
   - 在每 N 次推测解码迭代的调度点调用一次，开销平均仅占总执行时间的3.9%。

2. **草稿模型缓存管理器（Draft Model Cache Manager）**：
   - 在每调度点，从预测排序列表 R_i 中选取 top-K 草稿作为目标驻留集 W_i。
   - 对 W_i 中未驻留的草稿发起异步预取（async prefetch）；若空间不足，按预测效用升序驱逐非目标草稿，并尽量保护当前活跃草稿不被驱逐。
   - 采用简单的 top-K 策略，因为预测已捕获大部分效用差异。

3. **运行时控制器（Runtime Controller）**：
   - 核心原则：**始终执行当前驻留集中最优的草稿，绝不为非驻留草稿阻塞**。
   - 三项步骤循环：运行当前区间的推测解码 → 构建新上下文 → 进行预测和缓存更新，并选择下一区间的最优驻留草稿。
   - 若最优草稿尚未驻留，则继续使用当前可用草稿执行，同时后台加载更优候选。

**关键公式：**

- 吞吐量近似：Throughput ≈ E[A] / L_iter，其中 A 为接受token数，L_iter 为单次SD迭代延迟。
- 初始草稿选择：d_0 = argmax P(d | x_prompt)。
- 上下文构建：x_i = [x_prompt; x_recent_i(T)]。
- 目标驻留集：W_i = TopK(Sort(p_i))。
- 活跃草稿选择：d*_i = argmax_{d∈G_i} P(d | x_i)。

**两个核心设计原则：**
- **非阻塞执行（non-blocking execution）**：始终从驻留集中选择。
- **主动驻留管理（proactive residency management）**：让驻留工作集与预测的未来需求对齐，将草稿适配转化为分阶段、重叠的过程。

## 6. 论文的主要结论与发现

1. **静态选择不足**：Oracle-Static 比 General-Static 提升正常化接受率 40.3%，而 Oracle-Dynamic 再比 Oracle-Static 提升 25.7%，证明最优草稿在同一生成内部也会变化，静态选择不够。
2. **探索式自适应在内存受限下失效**：MAB-Sync 和 MAB-Async 虽提升接受率，但模型加载耗时占主导，MAB-Async 平均有 46.4%-49.4% 的时间在 fallback 执行（用次优驻留草稿），改善的接受率未能转化为吞吐提升。
3. **MemSpec 有效弥补选择性-可用性差距**：
   - 将 fallback 执行降至 5.5%以下，desired 执行比例大幅提升。
   - 预测开销仅占 3.9%。
   - 相比 General-Static 提升吞吐 58.8%，相比 MAB-Async 提升 40.7%，达到 Oracle-Dynamic 的 95-97%。
4. **预测与调度需联合优化**：仅靠预测（Prediction-Only）只能提升 21.6%，与完整 MemSpec 差 30.5%，说明没有主动缓存管理，预测质量不会转化为执行质量。
5. **预测器不需要完美**：Prompt+Recent 组合实现 top-1 准确率 71.6%、top-2 召回率 95.7%，保证高效用草稿几乎总在驻留集中即可。
6. **更长输出和中等调度区间更有利**：输出越长，自适应优势越明显；N=4~8 性能鲁棒，N=2 太小（频繁重调度），N=16 太大（延迟有益切换）。
7. **小驻留容量即足够**：在 Jetson AGX Orin 上从 K=2 增至 K=4，MemSpec 仅从1.47×微升至1.51×，而 MAB-Async 从1.13×升至1.29×，MemSpec 对容量需求更不敏感。

## 7. 优点
