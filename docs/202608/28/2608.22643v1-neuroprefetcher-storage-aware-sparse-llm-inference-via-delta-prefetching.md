## 摘要
在边缘设备上部署大型语言模型日益受到模型规模与可用内存之间不断扩大的差距的限制。现有方法如量化、更小模型和卸载可以提高有效内存上限，但它们仍然假设模型可以被压缩或分区以适应某个预算。我们针对更困难的“模型超出内存”场景，其中模型在整个执行过程中始终大于常驻内存，存储成为关键路径上权重的一个活跃来源。我们观察到自回归解码期间MLP活动具有很强的时间局部性：大约82-85%的活跃神经元从一个token持续到下一个。这意味着当前token所需的大部分稀疏权重已经常驻，只有新需要的行必须从存储中获取。我们提出了NeuroPrefetcher，一个利用这一特性通过预测性增量预取实现的存储支持型LLM推理系统。在第0层之后，一个占据基础模型参数2.86%的GPU常驻预测器在一次前向传播中预测所有下游MLP层的稀疏活动。运行时将这些预测与GPU常驻缓冲区进行比较，并仅为传入的增量行发出应用调度的NVMe读取，用显式的、模型感知的权重移动取代反应式的操作系统按需分页。在真实的统一内存边缘硬件上，NeuroPrefetcher在受限内存预算下比llama.cpp实现了7.9-12.0倍的加速。

## Abstract
Deploying large language models on edge devices is increasingly limited by a widening gap between model size and available memory. Existing approaches such as quantization, smaller models, and offloading can raise the effective memory limit, but they still assume that the model can be compressed or partitioned to fit within some budget. We target the harder model-exceeds-memory setting, in which the model remains larger than resident memory throughout execution and storage becomes an active source of weights on the critical path. We observe that MLP activity during autoregressive decoding has strong temporal locality: approximately 82-85% of active neurons persist from one token to the next. This means that most sparse weights needed for the current token are already resident, and only the newly needed rows must be fetched from storage. We present NeuroPrefetcher, a storage-backed LLM inference system that exploits this property through predictive delta prefetching. After layer 0, a single GPU-resident predictor, occupying 2.86% of base model parameters, predicts sparse activity for all downstream MLP layers in one forward pass. The runtime compares these predictions against resident GPU buffers and issues application-scheduled NVMe reads only for incoming delta rows, replacing reactive operating-system demand paging with explicit, model-aware weight movement. On real unified-memory edge hardware, NeuroPrefetcher achieves 7.9-12.0x speedup over llama.cpp across constrained memory budgets.

## 1. 论文的核心问题与整体含义

- **背景**：大语言模型（LLM）规模迅速增长，而边缘设备的内存容量增长缓慢（模型每代约增长10倍，边缘DRAM仅增长约2倍），导致“模型–内存差距”不断扩大。
- **核心问题**：现有压缩（量化）、小模型、卸载等方法都假设模型可以被压缩或分区以装入内存预算；论文针对更困难的**“模型超出内存”（model-exceeds-memory）**场景——模型在整个执行过程中始终大于常驻内存，存储（NVMe）成为关键路径上的主动权重供应层级。
- **后果**：在该场景下，传统系统（如llama.cpp）依赖操作系统的按需分页，导致大量页错误、CPU阻塞在I/O、GPU利用率极低（实测11,453次major faults/秒、CPU iowait 77%、GPU利用率仅3%），推理性能受限于反应式的权重移动而非算力。
- **整体含义**：论文提出NeuroPrefetcher，将存储视为可显式调度的权重层级，通过**预测性增量预取（delta prefetching）**，只从NVMe读取当前token新需要的稀疏权重行，从而绕过反应式分页的瓶颈，使模型超内存的推理在边缘设备上成为可能。

## 2. 论文提出的方法论

- **核心思想**：
  - 观察到自回归解码中MLP活跃神经元具有强时间局部性：相邻token约有82–85%的活跃神经元相同，因此当前token所需的大部分稀疏权重已在GPU缓冲区中，只需获取新增的“delta”行。
  - 将反应式的OS按需分页替换为**应用调度的、模型感知的显式NVMe读取**。

- **总体架构**：
  - 将模型分为**密集前缀**（前d层，MLP权重完全驻留GPU）和**稀疏后缀**（其余层的MLP权重以固定容量活动行缓冲区驻留，完整稀疏权重存储在NVMe）。
  - 第0层密集执行后，一个GPU驻留的**共享预测器**（参数仅占基础模型的2.86%）一次前向传播即可预测所有下游层（第1–31层）的gate和up投影的**质心ID**，从而提前获得整个稀疏层的I/O计划。

- **离线准备阶段**：
  1. **激活阈值化**：对每层MLP激活计算百分位阈值，将低于阈值的神经元置零，产生稀疏激活模式（文中使用α百分位，如62%、50%、31%稀疏度）。
  2. **聚类**：将阈值化后的二值激活掩码聚类为稀疏质心（centroid），形成固定大小的“质心库”（论文使用K=512个簇）。运行时只需预测每层每个投影的质心ID，而非逐神经元预测。

- **共享激活预测器**：
  - 输入特征包括：token嵌入、注意力前LayerNorm输出、注意力头草图（128维）、注意力后残差标量，以及第0层gate投影的质心ID（捕获激活结构）。
  - 结构：4个连续特征经独立投影块（线性+LayerNorm+SiLU+Dropout）变为512维嵌入，拼成4T维；质心ID经嵌入+投影网络也得到4T维；二者拼接为8T维，经残差MLP主干处理，最后由31个独立的gate输出头和31个up输出头预测质心logits。
  - 训练：交叉熵损失（gate CE + up CE），AdamW，分布式数据并行，batch size=2048 tokens/GPU，梯度裁剪1.0。
  - 规模：206.8M参数，FP16占414 MB，运行时固定一次/token。

- **预测性增量预取**：
  - 每层维护固定容量（K_max）的活动行GPU缓冲区，以及记录神经元是否驻留的槽位映射表S(l)。
  - 当前token预测的活跃集合A_t(l)与上一token活跃集合A_{t-1}(l)做集合差：得到**进入集合D_in**（需从NVMe读取）和**离开集合D_out**（释放槽位）。
  - 首次token（cold start）加载完整预测活跃集；之后只读取增量行。
  - SwiGLU结构下，中间神经元只在gate和up同时活跃时有效，因此用二者质心掩码交集确定活跃集；同一活跃集索引gate、up、down三套投影行。

- **I/O路径**：
  - 离线将稀疏MLP权重重打包为**神经元连续布局**（每24.5 KiB记录包含一个中间神经元对应的gate、up、downT三行），使单个记录读取即可获得该活跃神经元的所有投影权重。
  - 运行时会排序并**合并相邻活跃神经元ID**为连续读范围，通过Linux `io_uring`（O_DIRECT，队列深度256）提交异步NVMe读。
  - 读取先进入**主机端固定staging缓冲区**（`cudaHostRegisterMapped`，保证缓存一致性，避免Jetson统一内存上直接I/O导致GPU看到陈旧数据），再由融合CUDA scatter内核将记录解交织并写入各层GPU活动行缓冲区。
  - 整个I/O路径在背景线程执行，与密集前缀的GPU计算重叠。

- **内存自适应密集/稀疏划分**：
  - 通过自动化扫描选择最大可驻留的密集前缀层数d*；随可用内存收紧，引擎将更多的密集层转为稀疏执行（以更大的行级稀疏流量为代价），而不是退化为整层NVMe读取。

## 6. 论文的主要结论与发现

- 在模型超出内存的配置下，NeuroPrefetcher相比llama.cpp实现**7.9–12.0×加速**；在14 GiB内存上限时从0.34 tok/s提升到3.22 tok/s。
- 预测器可保留**92–96%的密集准确率**（HellaSwag），无需任务专门重训练；质心选择正确率约99%，质量损失主要来自聚类阶段而非预测误差。
- Delta复用率达**82–85%**，每token的NVMe读取量在9.0–14.8 GiB CUDA内存范围内仅从约1 GiB降至103 MiB，避免了整层NVMe读取的跳变。
- 密集前缀长度的选择存在三阶段效应（上升、峰值、下降），需要自动校准d*来平衡密集驻留与稀疏缓冲区空间。
- 即使采用delta预取，**NVMe I/O仍占每token延迟的80–87%**，是进一步优化方向。
- 在统一内存边缘设备上，传统双设备假设（GPU/CPU分离）的卸载系统多数无法运行；NeuroPrefetcher是该场景下最快且唯一专为稀疏存储支持执行设计的引擎。

- **稀疏度设置方式偏理想化**：
  - 使用固定K_max（每层恒定活跃数量）代替动态阈值；真实token的活跃神经元数量波动较大，固定预算可能造成过度剪裁或浪费读取。
  - 稀疏度通过离线百分位阈值设定，依赖预训练语料分布；跨领域分布漂移可能影响质心和质量（论文用HellaSwag部分验证了鲁棒性，但未做更多领域测试）。

- **质量与性能折中未充分探讨**：
  - 虽然报告了困惑度和HellaSwag，但没有展示不同任务类型（如代码、数学、多轮对话）下的表现。
  - 没有讨论预测器错误时的行为或容错机制（预测错误可能导致缺行/错误行，影响输出）。

- **I/O路径的技术债务**：
  - 缓存一致性staging依赖CUDA mapped host memory，仅适用于统一内存架构；标准PC平台可能需要额外处理（论文承认staging是Jetson特定）。
  - io_uring队列深度、staging大小等参数未做全面敏感性分析。

- **算力信息不完整**：
  - 未披露预测器训练的具体时间、epoch数、数据量（需要多少token计算/聚类），可能影响可复现性。

- **基线公平性**：
  - llama.cpp使用FP16权重且依赖mmap按需分页，未对比其量化版本或更积极的offloading策略；与FlexGen的对比只用了OPT-6.7B all-disk配置，未充分公平展示其性能（论文也承认这是“for completeness”）。

- **应用限制**：
  - 方法依赖SwiGLU/ReLU等可稀疏化激活；对于非ReLU类或全稠密模型（如某些Transformer变体）不适用。
  - 离线准备（聚类+训练预测器）需要A100集群等充足算力，小型团队或边缘场景中的部署成本未被讨论。
