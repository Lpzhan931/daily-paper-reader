## 摘要
推测解码通过使用轻量级草稿模型推测多个词元，减少昂贵的目标模型解码步骤，从而加速自回归大语言模型（LLM）推理。其有效性在很大程度上取决于草稿选择，这促使了利用输入和生成阶段差异的自适应方法。然而，在内存受限的边缘设备上，由于草稿模型之间切换的开销，这些方法往往无法提升端到端吞吐量。我们发现了该设置中的一个关键限制：在严格的内存预算下，草稿选择与草稿可用性之间存在不匹配。为解决这一挑战，我们提出了MemSpec，一种用于边缘设备上自适应推测解码的预测引导、内存感知运行时。MemSpec通过主动的驻留工作集管理将草稿选择与执行解耦。一个轻量级预测器根据提示和生成上下文估计草稿有效性，而一个内存感知调度器则减少响应式模型加载开销。在Jetson Orin Nano上的实验表明，与最先进的基于赌博机的自适应方法相比，MemSpec将稳态生成吞吐量平均提高了40.7%，同时接近Oracle上限。

## Abstract
Speculative decoding accelerates autoregressive large language model (LLM) inference by using a lightweight draft model to speculate multiple tokens, reducing expensive target model decoding steps. Its effectiveness depends heavily on draft selection, motivating adaptive methods that exploit variation across inputs and generation stages. On memory-constrained edge devices, however, these methods often fail to improve end-to-end throughput due to the overhead of switching between draft models. We identify a key limitation in this setting: the mismatch between draft selection and draft availability under tight memory budgets. To address this challenge, we present MemSpec, a prediction-guided, memory-aware runtime for adaptive speculative decoding on edge devices. MemSpec decouples draft selection from execution through proactive resident working-set management. A lightweight predictor estimates draft effectiveness from prompt and generation context, while a memory-aware scheduler reduces reactive model loading overhead. Experiments on a Jetson Orin Nano show that MemSpec improves steady-state generation throughput by 40.7% on average over state-of-the-art bandit-based adaptive methods while closely approaching the oracle upper bound.

## 1. 核心问题与整体含义

- **研究背景**：大语言模型（LLM）推理正从云端数据中心转向内存受限的边缘设备（如移动设备、嵌入式系统）。在严格内存预算下实现高吞吐 LLM 推理已成为关键系统挑战。
- **推测解码（Speculative Decoding, SD）**：通过轻量级草稿模型（draft model）生成多个候选词元，再由较大目标模型（target model）验证，以摊薄昂贵的目标模型解码开销。其效率严重依赖草稿模型的选择质量。
- **核心问题**：不同草稿模型在不同提示词和生成阶段表现出显著差异，因此需要**自适应草稿选择**。但在内存受限的边缘设备上，候选草稿模型无法全部驻留内存，切换到非驻留草稿需从较慢存储（如 NVMe）加载；一次模型加载耗时可达单个 SD 迭代的 2.7 倍，频繁的草稿切换会抵消甚至逆转自适应选择带来的吞吐收益。
- **根本矛盾**：现有探索式（如多臂老虎机，MAB）自适应方法只优化"选择哪个草稿"，却忽视了"该草稿是否立即可执行"——即**草稿选择与草稿可用性之间不匹配**。作者认为，边缘设备上的自适应推测解码不仅是**选择问题**，更是**内存约束下的调度问题**。

## 2. 方法论

- **核心思想**：MemSpec 是一个预测引导、内存感知的运行时系统。它通过**将草稿选择与执行解耦**，实现非阻塞自适应推测解码：预测器提前识别有潜力的草稿，缓存管理器主动维护驻留工作集，而解码始终使用当前驻留的最优草稿，同时后台异步预取更好的候选草稿。
- **整体架构**（图 5）：包含三个关键组件：
  1. **Prediction Engine（预测引擎）**：基于微调 BERT 编码器，输入提示词+近期生成词元，为每个候选草稿打分并排序。
  2. **Draft Model Cache Manager（草稿缓存管理器）**：在内存预算内维护一个小的驻留草稿工作集，协调预取与逐出。
  3. **Runtime Controller（运行时控制器）**：编排解码、预测、缓存更新与草稿切换，执行"始终选择当前驻留最优草稿、永不为非驻留模型阻塞"的策略。
- **关键公式与流程**：
  - 吞吐量近似：`Throughput ≈ E[A] / L_iter`，其中 A 为单次迭代接收词元数，L_iter 为平均迭代延迟。
  - 初始化草稿：`d_0 = argmax_{d∈D} P(d|x_prompt)`（仅基于提示词）。
  - 调度点上下文：`x_i = [x_prompt; x_recent_i(T)]`（提示词+最近 T 个生成词元）。
  - 预测打分：`p_i = {P(d|x_i) | d∈D}`，排序得到候选榜单 `R_i`。
  - 目标工作集：`W_i = TopK(R_i)`，即预测得分最高的 K 个草稿。
  - 实际执行草稿：`d*_i = argmax_{d∈G_i} P(d|x_i)`（**仅从当前驻留集 G_i 中选择**）。
- **调度机制**：每 N 次 SD 迭代执行一次预测与缓存更新（默认 N=4），将预测与加载开销摊薄到多个解码步骤中。预取为**异步操作**，与解码重叠执行。
- **缓存逐出策略**：需要空间时，按预测效用升序逐出不在目标集且非活跃草稿；尽可能保护当前活跃草稿不被逐出，保证解码不中断。

## 6. 主要结论与发现

1. **静态草稿选择不足**：Oracle-Static 相比 General-Static 平均提升接收率 40.3%，Oracle-Dynamic 进一步带来 25.7% 的提升，说明草稿有效性在单个生成过程中会动态变化。
2. **探索式自适应方法在边缘设备上失效**：MAB-Async 虽能改善草稿选择质量，但回退执行（执行次优草稿）占其总运行时间的 49.4%，提升的接收率无法转化为吞吐收益。
3. **MemSpec 显著提升吞吐**：在 Jetson Orin Nano 上，MemSpec 相比 General-Static 平均提升稳态生成吞吐 **58.8%**，相比 MAB-Async 平均提升 **40.7%**，并达到 Oracle-Dynamic 动态上限的 **95–97%**。
4. **组件消融验证设计**：Prediction-Only 相比 MemSpec 落后 30.5%，后者将回退执行从 21.3% 降至 5.3% 以下，证明预测+主动缓存管理缺一不可。
5. **预测器质量足够**：组合输入（提示词+近期词元）的预测器 Top-1 准确率 71.6%、Top-2 召回率 95.7%，说明不需要完美预测，只要保证高效草稿进入驻留集即可。
6. **核心洞见**：在内存受限边缘设备上，自适应推测解码的主要瓶颈不是草稿选择质量，而是**确保有效草稿的及时可用性**。

## 7. 优点

- **问题识别准确**：清晰揭示"草稿选择 vs. 草稿可用性"的错位，将自适应推测解码重新定义为**内存约束下的调度问题**，角度新颖且具有实际意义。
- **设计优雅实用**：选择-执行解耦、非阻塞执行、异步预取等设计简洁有效；预测器只要求"足够好的排序"而非精确效用估计，降低了对预测精度的苛求。
- **对比基准公平**：MAB-Async 采用异步加载+最优探索系数的较强变体；Oracle 上限提供明确性能参照，增强了结论的可信度。
- **实验解释力强**：通过执行时间分解和组件消融，从机制层面解释了性能提升来源（回退执行减少），而非仅报告最终吞吐。

## 8. 不足与局限

- **硬件覆盖有限**：主实验仅在一个边缘平台（Jetson Orin Nano）上完成；缓存容量分析转移到 AGX Orin，但未在不同内存带宽/容量的多个设备上系统评估普适性。
- **计算成本未充分披露**：草稿模型的蒸馏微调、预测器训练的具体算力消耗未报告，影响可复现性和实际部署成本评估。
- **场景覆盖较窄**：默认输出长度仅 128 词元、批大小固定为 1；未评估更长生成（如 long-form 生成）、并发多请求或更高批大小场景。
- **对领域草稿的依赖**：草稿模型集合需针对领域进行预训练/蒸馏，在真实开放域场景中如何构建与更新候选草稿集合仍不清晰。

- **端到端收益下降**：纳入启动开销后，MemSpec 相对 General-Static 的收益从稳态的 58.8% 降至 32.3%，说明短输出场景下自适应调度的收益有限。
